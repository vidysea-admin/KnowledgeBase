# WhatsApp connector setup

The tenant-owner resolver, connector source and focused tests are adopted. Production wiring is still a separate integration step: the sole integrator must apply the reviewed byte-preserving V3 production seam, then compile/review/deploy it and coordinate the owned API restart. The current running API has not loaded that integration. Adding a mapping alone does not activate it. Live capture and R2 acceptance remain unverified.

1. First choose the intended archive account/data source. Current main configuration points to a non-loopback archive; local installation is not automatically required. If a separate local archive is intended, build/start the separately governed `sources/whatsapp_msg` application according to its README and package-lock, with Node >=20. Use an isolated archiver Mongo database. Upstream names are `MONGO_URI` (default mongodb://127.0.0.1:27018) and `MONGO_DB` (default whatsapp_msg), plus writable `SESSIONS_DIR`/`MEDIA_DIR`. `PORT` defaults3000; `INVITE_CODE` is optional signup protection, `LOG_LEVEL` defaultsinfo, `SYNC_HISTORY` defaultsfalse (historical names discovery only, never old-message capture).
2. The account owner signs up/logs in using their local email/password. The existing UI explains unofficial-client account risk before QR; linking requires the owner's WhatsApp phone. Select tracked groups and senders, or the upstream explicit track-all mode. The socket must remain read-only: no sending, read receipts or presence. Main architecture Q4 is resolved by D008; this guide creates no new approval gate.
3. While logged in to the archiver, its authenticated `GET /api/me` returns `userId`, the canonical `users._id` Mongo ObjectId represented as24hex. An authorized administrator verifies this belongs to the intended account; do not derive it from phone numbers, tenant names, group IDs or client-supplied ingest bodies. Never expose passwordHash, session cookies or QR credentials. No account lookup was performed for this guide.
4. In the main API's trusted deployment configuration, set `WHATSAPP_MONGO_URL`/`WHATSAPP_MONGO_DB` to that isolated archiver database. These names differ from upstream's `MONGO_URI`/`MONGO_DB`. Give the main connector read-only archiver permissions; it writes derived sources only to its explicitly isolated LKB database.
5. After reviewed production V3 integration is deployed, set `WHATSAPP_TENANT_OWNER_MAP` to a JSON array, e.g. `[{"tenantId":"example-tenant","ownerUserId":"111111111111111111111111"}]`. This is synthetic syntax, not an actual account grant. Use verified real authenticated LKB tenant identities and actual archiver user ObjectIds. This mapping is server-owned, never accepted from HTTP input. One archiver owner may map to only one LKB tenant under the current source-ID design. Different owners can independently track the same groupJID. Duplicate owner grants are refused because source/session hashes currently omit tenant, and globally unique Mongo `_id` would collide across tenants.
6. Missing/blank/empty mapping disables only WhatsApp access: its calls refuse before source DB reads/app writes/indexing. Invalid JSON, unknown fields, blank/whitespace tenant IDs, non24hex owners or duplicate tenant/owner grants fail configuration with a sanitized setup diagnosis. Optional WhatsApp/Tavily absence is not a universal API startup prerequisite; an explicitly malformed mapping is a configuration error, not a missing-provider requirement.
7. An authorized API key needs the existing `whatsapp` scope; requests select only `groupJid`. Empty configured archive yields an empty group list; a configured tracked group with zero captured messages yields zero turns, not invented knowledge. Do not call zero-turn ingest an R2 success. Current production index wiring may attempt indexing, and source-review/extraction/retrieval gates must independently pass. The message snapshot race has a separate work-only fix under independent review; do not treat it as deployed until its source adoption and runtime integration are verified.

Current main `.env` presence-only audit: WHATSAPP_MONGO_URL and WHATSAPP_MONGO_DB PRESENT; WHATSAPP_TENANT_OWNER_MAP ABSENT. Upstream keys are absent from that main file; the separate archiver `.env` was not inspected. Values were neither copied nor printed, and the main file was preserved.

Keep account identifiers and credentials in trusted local deployment setup, not chat. The operator still needs an administratively verified archiver account userId and an explicit tenant grant; no owner account or local/remote deployment choice is assumed by this guide. The snapshot fix changes no production composition signature or resolver contract.
