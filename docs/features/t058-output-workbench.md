# Knowledge output workbench (T-058)

The authenticated `/knowledge-outputs` page builds FAQ answers, reports and meeting preparation drafts from selected session evidence. FAQ answers include questions; reports separate executive summary, insights, recorded decisions and suggested risks; meeting briefs separate background, suggested agenda, questions and suggested risks. Every supported item links to the actual source turn and quotation.

Generation uses the established tenant-bound `answer` provider chain. A separate model call assesses each item against its exact canonical quotations. These checks are AI assessments; they do not establish human verification. Unsupported items remain withheld and missing sections remain visible. The source-coverage field also records eligible versus partial evidence and the count of unverified or unresolved claims excluded from generation; a refusal policy cannot label that partial selection ready. Source material and the user's purpose are supplied as untrusted data in a fixed prompt. Requests allow at most ten sessions, 200 candidate claims, 4,000 turns, 100 citations and 60,000 source characters; model calls time out after 30 seconds each. A late provider completion cannot persist an output through the timed-out service call.

Drafts persist in the schema-first `knowledge_outputs` collection. Writes and reopened reads validate the actual JSON schema with Ajv2020/formats and enforce canonical section roles/identities, reference uniqueness/existence and source ranges/links; damaged records fail closed. Each supported item's assessment fingerprint binds its exact text, identity, role and citation IDs to the source digest, so stored text damage cannot retain a stale assessment. This fingerprint is a consistency check, not human verification or a signature against database administrators. The repository scopes every read/write by the verified key's tenant. Revision comparison prevents concurrent edits from overwriting each other. Saving factual edits marks them `needs-review` and clears that fingerprint; explicit revalidation is required before Markdown export. Users can remove items; the remaining coverage stays visible. Citation mappings are read-only. Export checks the current source/quote/turn attribution and policy snapshot against the generation digest. Changed, deleted or newly unverified evidence requires regeneration. The Markdown artifact preserves AI-draft status, missing coverage, exact quotations, source identity and source links, and escapes Markdown/HTML input.

Source reads apply T-054's actual current transcript correction projection, then T-007's current knowledge-visibility capability. Corrected text and attribution contribute to the source digest without modifying immutable original turns; old drafts require regeneration. WhatsApp sessions appear only through the safe generic citation projection; raw group titles, participants and unapproved message siblings never become builder evidence. Eligibility requires the authoritative current approved candidate and materialized claim, exact current source evidence and no pending invalidation. A fresh check on every reopened read and export refuses revoked or changed evidence. Actual message occurrence timestamps are retained in citations and model input instead of presenting zero-second offsets as an event time. Excluded ordinary visible claims count toward partial coverage; private unapproved WhatsApp counts are not exposed.

The workbench consumes T-056's effective policy lookup. The policy question class is the output kind (`faq`, `report` or `meeting-brief`). A selected current policy controls concise/detailed style and refusal on incomplete support; conflicts refuse generation. Required citations cannot be relaxed. The builder uses internal evidence even when a policy also permits web. No matching policy uses a visible conservative internal-only default. Changed/retired/conflicting policy snapshots cannot authorize a stale export.

API routes must be mounted after the established authentication middleware. All require `sessions`; create/edit/revalidate additionally require `ask`. Create accepts only kind, title, purpose, selected session IDs and optional policy ID. Tenant, citations and generated text are never accepted as authority from clients. Read/list/export and cross-tenant output IDs use the same tenant boundary. The create router returns a fixed error on provider failures without echoing prompts or credentials.

`createConfiguredOutputService(db, tenantBoundComplete, answerPolicyService)` is the production integration seam. The central writer owns its server/composition mount, web route/nav, schema, generated type and migration. The new store refuses protected production databases; other feature opt-ins do not authorize T-058 writes. A missing store exposes truthful 503 responses.

Source implementation is distinct from complete task acceptance. Focused fixtures can exercise model response validation, auth, tenancy, CAS, edit/revalidate/export and UI HTTP consumption. They do not establish actual provider usefulness or durable live Mongo behavior. The existing TOC sample has unreviewed claims: it must refuse factual generation, rather than silently changing source verification. A clearly labelled in-memory verified copy can demonstrate downstream mechanics without changing raw files. Actual reviewed sample/provider outputs, isolated Mongo restart/isolation, independent browser flows/citation click-through and Umesh's acceptance of all three products remain required under `qa/contracts/goal-t058.md` before T-058 is done.
