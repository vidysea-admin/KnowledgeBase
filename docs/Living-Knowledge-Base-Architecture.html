Hybrid design: vectorless tree-index (mirrors our own /brain — operating-brain/wiki/INDEX.md) for the structured session archive, traditional vector RAG reserved for future unstructured content, and a CRAG-style query router that trusts internal knowledge first and only falls back to the web when internal coverage is insufficient — exactly the flow described in vision.md.

Key reading order:
① Ingestion — a recording usually exists and goes through transcription via the Gemini API (cloud, audio-native) — chosen over relying solely on the local faster-whisper/CUDA pipeline, which has already hit a real dependency failure once (missing cublas64_12.dll during the original 23-session run). The existing local /transcribe skill is kept as a fallback, not removed. Piloted transcription pipeline (validated end-to-end on the 27th-August session): gemini-3.5-transcribe diarizes the FULL session in one call (no missed turns — proven not to truncate) → the same model re-runs with word-level timestamps on 8-10 min audio chunks (chunking needed only for timestamps, not diarization) → gemini-3.7-flash merges the two, maps generic speaker labels to real names only where a name is actually stated (escalating to gemini-3.1-pro-preview if that pass looks incomplete), and stays silent rather than guessing where a name was never said. This produces a speaker-wise, timestamped transcript (who said what, and when, per speaker turn — the 23 existing transcripts don't have this) plus a separate session summary generated from it; both feed the per-session page in ②. When no recording exists at all, the process-first fix kicks in: standing ask to Bhakti/TOC; if it never arrives, the session is logged as a "recording pending" gap entry rather than silently dropped. Docs/collaterals follow the existing csv/xlsx conversion path. WhatsApp and a live meeting-bot are shown as future sources only — not built this round. ② Indexing mirrors our own /brain: transcripts and gap entries get synthesized into per-session pages, folded into KNOWLEDGE-BANK.md, and rolled up into a regenerated TOC-INDEX.md tree router — vectorless, no embeddings, same shape as operating-brain/wiki/INDEX.md. A separate vector-RAG branch is reserved for raw unstructured WhatsApp text once that source exists. ③ Query is the CRAG-style router vision.md asked for: a question walks the tree (the automated version of what /brain does by hand today), an evaluator scores what came back, and only when internal coverage is incorrect/ambiguous does the system reach out to the web — internal knowledge stays authoritative, web is the fallback, and every answer is cited. ④ Maintenance loop is what makes it "living" — every new session re-enters at ① and ②, and the existing by-month Google Sheet (already shared) gets its new row automatically instead of by hand.

TOC LIVING KNOWLEDGE BASE — STEP-BY-STEP FLOW (plain text export)
Hybrid architecture: vectorless tree-index (mirrors our own "/brain" — operating-brain/wiki/INDEX.md)
for the structured session archive, plus a CRAG-style query router that trusts internal
knowledge first and falls back to the web only when internal coverage is insufficient.

STATUS KEY: [EXISTING] = already working today · [NEW] = new in this design, piloted on 1
session so far · [FUTURE] = explicitly not built this round

================================================================
LAYER 1 — INGESTION (per source type)
================================================================
1. A TOC session happens.
2. DECISION: Is a recording available?

   2a. YES -> Transcription pipeline [NEW, primary — validated end-to-end on the
       27th-August-In-Focus session]:
       - gemini-3.5-transcribe, diarization=True, ONE call over the full session
         audio -> speaker-separated turns (spk:0, spk:1, ...), verbatim ASR text.
         Proven not to truncate for a ~50 min session (finish_reason=STOP).
       - gemini-3.5-transcribe again, word_timestamp=True, run on 8-10 min AUDIO
         CHUNKS of the same file (word-level timestamps are too token-heavy for a
         full session in one call — chunking is needed only for this step, not
         for diarization).
       - Align: match each turn's first few words against the chunked word-timestamp
         list to assign every turn a real [MM:SS] start time.
       - gemini-3.7-flash: ONE pass over the full turn list. ONLY job — replace a
         generic speaker label (spk:N) with the real name wherever that name is
         actually stated in the dialogue (self-intro, host intro, etc.); leave the
         label generic if no name was ever said (do not guess). Escalate to
         gemini-3.1-pro-preview if this pass looks incomplete (output shorter than
         ~70% of the input).
       - [EXISTING, fallback] local /transcribe skill (faster-whisper, CUDA) is kept
         as a fallback path — used only if Gemini is unavailable. It already hit a
         real failure once (missing cublas64_12.dll dependency).
       - The full diarized transcript stays linked as source, same convention as
         today's Transcripts/*.content.md.
       - gemini-3.7-flash: ONE more call on the finished transcript -> SESSION
         SUMMARY (250-400 words, cites concrete numbers/programs/pricing actually
         present in the transcript, does not invent facts).

   2b. NO -> Process-first gap handling [NEW, process not code]:
       - Standing ask: request the recording from Bhakti / TOC.
       - DECISION: received within N days?
           - YES -> joins the transcription pipeline above (2a).
           - NO  -> logged as a "recording pending" gap entry in the Knowledge Bank
             (not silently dropped).

3. Docs / PDFs / Excel collaterals -> existing csv/xlsx conversion -> structured
   tables. [EXISTING]

4. [FUTURE, not built this round] WhatsApp messages — D:\whatsapp_msg's MongoDB,
   filtered by TOC's group jid. That archiver isn't pointed at TOC's group yet and
   has its own documented scaling concern (TASKS.md T-014).

5. [FUTURE, not built this round] Live meeting-bot — auto-joins Zoom/Meet/Teams to
   record automatically. Shown as an alternative to the process-first ask (2b), not
   built now — heavier lift (multi-platform browser automation, consent/TOS).

================================================================
LAYER 2 — STRUCTURING / INDEXING (vectorless tree, mirrors /brain's INDEX.md)
================================================================
6. Diarized transcript + session summary -> synthesize into a per-session page
   (mirrors an operating-brain deep-page shape). [NEW]
7. Append that page's summary into KNOWLEDGE-BANK.md, month-wise. [EXISTING pattern,
   now automated]
8. Build / regenerate TOC-INDEX.md — an LLM-authored hierarchical tree:
   by month -> by session -> by topic / speaker / featured-org.
   Vectorless: no embeddings, no vector DB — same shape as our own
   operating-brain/wiki/INDEX.md. [NEW]
9. [FUTURE, not built this round] Separate branch: unstructured WhatsApp text (once
   captured) -> traditional vector-RAG index (chunk -> embed -> Chroma/FAISS). Kept
   separate from the tree index because vectorless RAG degrades on content with no
   logical section boundaries.

================================================================
LAYER 3 — QUERY (CRAG-style router — the "living" behavior)
================================================================
10. A user asks a query.
11. Tree-search over TOC-INDEX.md — an LLM reasons over the tree and picks the 1-3
    most relevant session pages. (This automates what /brain does manually today.)
12. Retrieval evaluator scores the relevance of what was found.
13. DECISION: verdict?
    - correct -> answer generated from internal pages only, cited by session date +
      speaker. [terminal / delivered]
    - incorrect / ambiguous -> web search fallback, merged with any partial internal
      context -> answer generated from internal + web, with web sources cited
      separately from internal ones. [terminal / delivered]

    This is the internal-knowledge-first, web-second behavior vision.md asked for —
    the tree index plays the role CRAG's vector DB plays, and only insufficient /
    ambiguous internal coverage reaches outward.

================================================================
LAYER 4 — MAINTENANCE LOOP (what keeps it "living")
================================================================
14. New content lands — a recording, a "recording pending" gap entry, or a collateral.
15. Re-run Layers 1 -> 2: transcribe (or use gap entry) -> synthesize per-session page
    -> regenerate TOC-INDEX.md.
16. Append the new row to KNOWLEDGE-BANK.md.
17. The existing by-month Google Sheet (id 10IJsqWukIOkVaFDzkpWNnvJZ4olOdncDdC-d0vXJr6Q)
    gets a new linked row automatically — no manual update. [EXISTING sheet, automated]
18. Loop back to step 1 — this repeats for every new TOC session.

================================================================
PILOT RESULT (27th-August-In-Focus session, ~50 min audio)
================================================================
- Diarization call: 1 call, 47 speaker turns, no truncation (finish_reason=STOP).
- Word-timestamp pass: 6 chunks of 10 min, 8,621 words total, no truncation per chunk.
- Naming pass (gemini-3.7-flash): correctly named 6 of 7 distinct speakers from
  context; left 1 turn as a generic label rather than guess, because that speaker's
  name was genuinely never stated in that turn — the honest/conservative behavior
  this pipeline was chosen for.
- Summary output surfaced concrete details a single-call approach (gemini-3.6-flash
  reading the audio directly) had missed: exact program cadence, mentor background,
  enrolment-window status.
- Cost shape: ~9 API calls total per session (1 diarize + 6 chunks + 1 naming + 1
  summary). Audio-input token cost is duration-bound, not call-count-bound, so
  chunking for timestamps does not multiply the dominant cost.
