## What the present code actually guarantees

`apps/api/src/indexing/tile-speaker-suggest.ts` delegates its real insert through optional `publication.write`, but the adapter is not itself an atomic fence. `packages/db/src/collections/speaker-suggestions.ts:insertSuggestionsIfAbsent` performs separate `$setOnInsert` upserts. `apps/api/src/transcript-review/store.ts:insertHead` inserts the first head independently; `replaceHead` and `setRefresh` independently update heads. None writes sessions. Reading an absent head under snapshot isolation does not prevent a concurrent first insert. Reading sessions/sources and issuing an unchanged `$set` is not a dependable write conflict.

Useful existing pieces: `indexing/post-commit.ts:publishIndexWithCommit` and `transcript-review/refresh-executor.ts` use explicit snapshot/majority transactions and retry commit acknowledgement only. `transcript-review/transaction-db.ts:transactionReviewDb` binds tenant-scoped calls to one ClientSession, serializes operations and overlays effective turns. It already supports `$inc` through updateOne and transaction-bound suggestion upserts; reuse it rather than invent an alternate DB wrapper. Its `turns` writes are intentionally forbidden, so raw-ingestion transactions need a distinct narrowly scoped writable view, not weakening this guard.

## Minimal proposed schema and transaction protocol

Propose OPTIONAL `sessions.nativePublicationRevision`: JSON Schema integer, minimum 0, maximum 9007199254740991. Generated type only via gen:types. Missing means native publication disabled, never implicit zero. A migrate-mongo change initializes existing rows safely before enabling writers; fresh sessions initialize zero. Every increment checks safe-integer range and matchedCount/acknowledgement, fails closed at exhaustion. Never reset, import from source JSON, or restore an older counter. No new collection. This is an explicit schema proposal requiring root/Approver disposition, not covered by current central lease. Current frozen contracts/contracts.json stages is empty, but schema-first/migration rules and qa/contracts remain authoritative; no frozen or QA contract edits by the maker. Any new freeze/enforcement change needs its normal approval path.

After genuine archive/clock/sidecar verification and candidate calculation OUTSIDE Mongo, publication starts one explicit transaction. Through transactionReviewDb, read current sessions/source/head/effective turns and verify exact tenant/session/source, acknowledged complete generation, attempt turnDigest, current review revision OR absence, complete refresh targets, source hash/capture generation/receipt hashes and expected revision. Perform a REAL `$inc:{nativePublicationRevision:1}` with filter on the exact observed revision, sourceId and complete index attempt/generation/digest. A mismatch throws and rolls back. Recompute confirmed/rejected suppression INSIDE this transaction, then insert the entire candidate batch through insertSuggestionsIfAbsent using only the transaction-bound view. All rows commit together; no outside-handle upsert or partial success. Snapshot head/source reads are safe only because ALL relevant writers below contend on the same session counter in the SAME transaction as their mutation. Never treat the newly incremented counter as human acceptance.

No provider/decoder/FFmpeg work inside transaction retries. Prefer explicit startTransaction like existing publication code: bounded commit-only retry for UnknownTransactionCommitResult; unresolved acknowledgement returns unknown, not inserted=0 or success. Transient write conflict aborts the whole unit; an explicit bounded later attempt rereads every authoritative binding and suppression decision before reusing immutable candidate calculation. Duplicate deterministic IDs preserve existing suggested/confirmed/rejected rows. Empty/rejected batch need not publish. Suggestion results remain proposals, never confirmed speaker writes or fabricated human labels.

## Every writer that must participate

1. `transcript-review/store.ts`: insertHead MUST transactionally bump sessions AND insert head, including the first absent-head case. replaceHead MUST bump with its successful expectedRevision CAS; a lost CAS rolls back increment. setRefresh MUST bump with each successful state change, including pending/failed/source-reconciliation invalidation and completed progress. recordRevision is append-only history, not authoritative current binding, and does not need a fence by itself. `service.ts` currently documents the head CAS as commit point; revise that documentation/behavior to acknowledged joint commit without rerunning human plans blindly on unknown outcomes.
2. `transcript-review/refresh-executor.ts`: its final direct heads.updateOne bypasses store.setRefresh; increment sessions in that SAME outer refresh transaction. Preserve existing derived-target atomicity, generation updates and commit-only retry. No inner commit/hook. `indexing/generation.ts` already truly changes the session for acquire/enter/fail/complete, which conflicts with publication's session write; consistently bump revision in those same writes so a captured counter is also a complete invalidation token. Nested index inside refresh shares its transaction.
3. `scripts/webinar/sync-session.mjs`: current source upsert, session upsert and raw turn replacement are separate writes BEFORE indexing. Native-enabled source/consent/association/turn replacement must be a joint transaction including session increment and invalidation of old index eligibility before indexing. Do not retain done/indexAttempt validity across changed input. Keep source construction outside transaction. Adapt `session-rows.mjs:replaceSessionRows` only if required by chosen transaction view; do not weaken tenant scopes.
4. Source mutations to hash/path/captureConsent/consent/privateWindows/guardedPrivateWindows/operationalApproval/organizerConsent/captureMode, session.sourceId, raw turns, or deletion must transactionally bump ALL currently associated sessions of that tenant. New association also bumps the destination session. Serialize association creation through an actual write on the source document when association discovery could race; merely querying sibling sessions has a phantom-insert gap. For this bounded native recording slice, use a trusted single-owner session/source association and reject sharing/reassignment unless its corresponding transaction protocol is implemented. No generic raw sources accessor can imply automatic fencing.
5. Known alternate writers must be explicitly excluded for native recording rows or adapted before claiming universal coverage: scripts/seed-toc.mjs (insert-only duplicate failure, must not import a native counter), scripts/watch/lib/reingest-swap.mjs including restoreOldRows (currently compensating delete/reinsert, NOT atomic), apps/api/src/source-intake/store.ts (insert/compensating cleanup), apps/api/src/ingest-store.ts and whatsapp/store.ts (new unrelated kinds), packages/ingest/src/intake.ts caller stores. Reject native capture rows at these paths if not routed through the shared protocol. Do not expand this slice into generic document/WhatsApp rewrites. connector-workflow/mongo-store.ts changes only sourceMeta.connectorIndex; it is not receipt/consent mutation. Native document head-store and WhatsApp review paths are distinct source kinds and must not be advertised as covered native capture revocation APIs.
6. Human suggestion confirm/reject is another real race: deterministic same-row `$setOnInsert` protects that row, but a different conflicting pair can appear after suppression reads. For the stronger promise that no new competing native suggestion races a human decision, make confirmSpeakerSuggestion/rejectSpeakerSuggestion contend on the session fence in their decision transaction (including final speaker repair), and rerun suppression inside publication. Otherwise explicitly retain only same-ID no-overwrite guarantees. Never auto-confirm to close this gap.

## Filesystem consent and authority boundary

Current consent receipt/readRecordConsent and archive/source/measurement files live outside Mongo. Mongo cannot atomically certify their future bytes. Native capture proof must be immutable content-addressed admitted bytes held under the trusted writer boundary, with DB-authoritative current eligibility/binding. A receipt mutation/revocation protocol must FIRST commit DB invalidation plus session increment, THEN update/replace filesystem material; crash leaves disabled/pending. Re-enable only after immutable new artifacts have been independently verified and their exact binding committed transactionally. The active capture controller may continue recording privacy, but cannot silently rewrite a currently eligible published binding. If uncontrolled filesystem revocation remains authoritative, the requested strict publication fence is impossible: rechecks are only observations. Reject configuration/keep native publication unavailable rather than claim OS/DB atomicity. Archive published journal remains a recovery hint.

This transaction proves eligibility at the DB publication linearization point; later revocation does not erase already published suggestions automatically. Serving/confirmation must check current eligibility or revocation must transactionally suppress associated pending native suggestions. If machine-readable per-suggestion binding is needed for that policy, separately propose schema/speaker_suggestions.schema.json changes; do not hide authority in evidenceQuote prose. Historical human confirmations are not silently revoked or rewritten.

## Mandatory broker/checker evidence

- Positive: genuine qualified registry -> existing actual tile consumer -> transaction-bound real upsert batch -> acknowledged commit; all rows suggested only; authoritative current binding and effective turns match.
- Deterministic barriers: pause after snapshot reads and before writes; concurrent review FIRST insert, replacement, refresh invalidation/completion, index acquire/complete, source reassignment/hash/receipt/consent revocation and raw-turn replacement each commits in the other transaction. Publication must conflict/refuse with zero partially inserted rows. Reverse scheduling proves valid publication can commit first, followed by revocation/invalidation, without claiming impossible retroactive ordering.
- No-op regression: demonstrate real increment modifiedCount=1; deliberately remove participating writer bump in a disposable fixture and show first-review race is detected by tests. This is not production mutation testing.
- Wrong tenant/session/owner/revision/missing counter/exhaustion; multirow second-upsert failure; all suppressed/no-evidence; duplicate callback/restart IDs; conflicting human decision on a different pair if that stronger guarantee is selected; original confirmation/provenance unchanged.
- Commit failures: abort before commit, transient conflict, acknowledged retry, UnknownTransactionCommitResult then success, permanently unknown commit and reconciliation; no callback work/provider replay, no falsely exact inserted count, no archive hint treated as truth.
- Filesystem/DB crash ordering: invalidation committed before file change; crash before new binding remains pending; source/receipt bytes changing during proof never upgrade authority. Immutable proof validation retained separately from Mongo eligibility.
- Real standalone Mongo refuses transaction publication with zero suggestion writes. Current environment lacks replica-set operational proof: mocked transaction fixtures prove software paths only. Required real replica-set positive/race/rollback tests remain HOLD until explicitly available; no host activation or DB provisioning authorized here.
- Same-candidate mandatory contracts, types, scoped structure/cycles, affected stage/downstream checks and independent managed-review/1 verdict after sole broker runs; no review or PASS is issued by this planning artifact.
