## Smallest proposed implementation boundary

1. Add one scheduled-only Node entry/helper, proposed `packages/meeting-bot/src/calendar/scheduled-dispatch.ts`, and one CLI branch such as `record-scheduled <jobKey>`. Have the launcher's `-Job` branch pass only the validated job key to that entry. Keep the existing direct `record <url>`/direct `-Url` path and its manual authorization semantics unchanged. Do not implement gate logic twice in PowerShell and TypeScript. `-Job` must not permit URL/session overrides to bypass the checked item.
2. The helper loads the existing environment/runtime root, validates configured `LKB_TENANT_ID`, and uses `readScheduledJob(stateDir, jobKey, tenantId)` from `calendar/state/schedule-dedup-state.ts:180-188`, which calls `assertTenantTag`. Do not use the launcher's unchecked JSON parser as authorization. `writeScheduledJob` at lines 165-175 already writes a server/runtime supplied `tenantId` tag. The existing `ScheduledJob` shape contains only URL/until/title/sessionId and optional display/topic fields; it does **not** retain organizer/source identity, so merely checking the URL cannot implement sender/domain deny or id-only opt-out correctly.
3. Extend the saved job with a validated, versioned dispatch item retaining the selected `AutoRecordItem` fields: source, sourceId, sender when present, start/end time, URL and sessionKey. Bind those fields to the legacy capture fields; refuse mismatches and malformed/foreign/missing identity for enforcing dispatch. Bound any additional aliases to proven occurrence identities; do not synthesize series/shared-room aliases or expand known T037 cross-source exceptions. Persist only what current selection actually proves. Coordinate schema/writer edits with the scheduler/state owner; older jobs need an explicit refusal/reschedule migration behavior rather than invented source identities.
4. Verify the current API key tenant at dispatch with the existing `calendar/join-rules-wiring/key-tenant.ts` loader, using the same configured API base/key. Configured tenant, actual key tenant and saved job tenant must agree before rule/cache use. No key or profile material in logs.
5. Reuse the existing policy semantics at `calendar/join-rules/join-rules-enforce.ts` on a singleton validated selection with `readOnly: true`; use `join-rules-select.ts`/canonical ingest evaluator, never a second matcher. Current authoritative rules live under `raw/webinars/join-rules/<tenant>.json` through `packages/ingest/src/join-policy/join-rules-store.ts` (bot compatibility export). Approved `last-valid` behavior uses the existing tenant-bound integrity-checked `.last-valid.json` snapshot and original one-hour age; dispatch must not write/refresh either primary or snapshot. Preserve the configured mode's existing semantics; changing defaults/fail-open behavior requires its own explicit authorization. Missing, corrupt or foreign identity is a dispatch refusal independently of mode.
6. Only after the item survives the gate should the helper enter the existing `claimedRecordWithDefaults` and `runRecord` chain. Preserve duplicate claims, argv quoting, detached launch and liveness behavior. Emit fixed refusal reason tokens, not URLs/profile contents. No rules mutation, task cancellation or recording termination is necessary for this bounded unit. The check-to-launch race remains a material limit; this proposal proves updates saved before the gate, not instantaneous revocation after capture begins.
