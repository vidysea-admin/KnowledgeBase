## Criteria
1. Two owners in one tenant: A's session gets A's sessions and review candidates and 404 for B's raw session id; an admin sees both; an admin read of B's raw content writes an audit event.
2. A viewer and a non-owner member get 404/403 on raw WhatsApp sessions, turns and candidates, and still get approved claims through Search/Ask (Q2=2a); never raw turns of an unapproved candidate; never any content from tenant B.
3. ISS-API-003: the ledger's recorded reproductions re-run verbatim; report `ISS-API-003: n/n` refused to echo raw upstream text; the 502 body is `{error, code, linkId}` only.
4. Cross-owner duplicate: the same message captured by A and B yields one candidate flagged `duplicate` with a pointer, neither auto-merged nor dropped.
5. Legacy links are admin-only to read.
6. Adversarial: guessing a candidate id from another owner, replaying an approve with a swapped tenant header or body, sending `groupJid` of another owner, using a Bearer key without `whatsapp-admin` against a non-legacy link; all fail without side effects.

4. **`GET /sessions` list is metadata only and is not audited.** Detail reads by a non-owner admin are audited (count = turns returned). The review-queue list is audited per foreign link.
5. **Reviewed-guidance views of WhatsApp sessions are no longer shown to other members** through `GET /sessions` (404). Approved claims still reach Search/Ask/citations through the separate trusted readers (Q2=2a); a checker should confirm that path against the claim readers, which this unit did not alter.
6. **The duplicate pointer is the opaque candidate id of the other owner's earlier capture.** Not dereferenceable by a non-owner (the candidate route 404s), but it confirms that another capture of the same text exists in the tenant. Accept or tighten to a boolean plus count.
7. **4 tests (outside this unit's two files) need a real replica-set Mongo and are skipped locally.** The fake Mongo fixtures were used, so transactional behaviour of the duplicate, stamp and marker writes is not proven against real Mongo here; checker A ran its own real-mongod probe at cycle 0 and may repeat it.
8. **Ingest now makes one extra `listGroups` call to the archive before each ingest** (authorize-then-resolve); the store's own resolution still runs inside `ingestGroup`. A group removed between the two calls fails the second with the usual 404.
9. **Revoked/suspended gate (answered 2026-10-30):** an owner whose link is not `active` loses raw read access; an admin still reads and is audited. Terminal-state data is not deleted.
10. **`getSessionAsset` (media/frame routes) still calls the session lookup without a read context**; a WhatsApp session has no local media, so nothing raw is reachable, but it is not part of this fix.
