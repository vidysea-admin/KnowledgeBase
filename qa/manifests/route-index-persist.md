## Criteria
- C1 A cold `/route` index (new process, empty in-memory cache) is read from the persisted `route_index` document when its stamp equals the current stamp; the trusted tree is not read.
- C2 A persisted document whose stamp differs from the current one (shared visibility fingerprint OR tree root `indexRevision`) is never served: the tree is rebuilt and the document is overwritten in place (one document per tenant). The same holds for a structurally damaged document.
- C3 Tenancy: tenant A never reads tenant B's persisted index. Every `route_index` read and write is tenant-scoped (`tenantId` on the document, `_id` = tenantId, filter carries the tenant), and a document or node stamped for another tenant is rejected.
- C4 Failure and deadline: a failing or hanging `route_index` read falls back to the in-memory build inside the request deadline (bounded to half the time left, at most 1 s); a failing write never fails a request; the 3 s hard deadline, 503 mapping and `fingerprintWithin` bypass are unchanged (router untouched).
- C5 The write is an idempotent upsert: persisting the same state twice leaves one equal document.
- C6 Schema-first and no bypass: `schema/route_index.schema.json` (+ fixtures, generated type, `packages/db` accessor on `scopedCollection`); writes use the API's normal DB handle (`deps.db ?? getDb()`); no production opt-in, `isProtectedWorkDbName` untouched.
- C7 The in-memory index stays the hot layer: a warm index touches neither `route_index` nor the tree; an expired one refreshes from the persisted document, not from a tree rebuild.
- C8 `docs/api/route-endpoint.md` and `docs/DATA-STORES.md` say the route index is now persisted (R1 row, section 3 row, unit list, endpoint cache and latency sections).
- C9 Cold-start before/after is measured on the synthetic corpus and recorded here.

## Design notes (what is NOT a claim)
- Stamp = visibility fingerprint + tree `indexRevision`. The brief asks for the fingerprint; the fingerprint hashes sources, sessions, review heads and WhatsApp links but NOT the tree document, so a re-index that rewrites the tree without changing any session status would leave a fingerprint-only stamp stale. `generation.ts:148-152` and `native-evidence/publication.ts:116` bump `indexRevision` on every tree write, so it is added to the stamp (one projected read of the root). It is strictly more conservative: any difference rebuilds.
- Stamp is read BEFORE the tree. A change racing the build leaves the stored stamp older than the data, never newer, so the next reader rebuilds. Two writers racing are last-writer-wins and still safe for the same reason.
- "Rebuilt when sessions are indexed/re-indexed or their visibility changes" is implemented lazily, on the next read after the stamp moves (write-through). Eager rebuild inside the indexing pipeline is NOT wired: `apps/api/src/indexing/*` is outside this unit's file list. Consequence: right after a deploy or a re-index the first `/route` per tenant still pays one tree build (the build keeps running after a 503 and is written back, so the following request is warm).
- No migration: the only access path is `_id` (= tenantId), so no index is needed; the collection is created by the API on its first write (same as the 25 collections listed under M7 in docs/DATA-STORES.md). `tree_index` also has no `schema/index.json` entry. No `$jsonSchema` validator is therefore attached to the collection; the schema is enforced in code (`routeIndexFromDoc`) and by `schema/validate.py` fixtures. First write into `lkb_prod` happens when the deployed API serves its first `/route`: nothing was written to `lkb_prod` or `lkb` by this unit (fakes only).
- Document size: one document per tenant (Q7 in docs/DATA-STORES.md). Measured 64,329 bytes for 22 sessions / 132 nodes (about 490 bytes per node); the reader's cap of 10,000 nodes is about 5 MB. A serialized document over 12 MB is not written (event `skipped-oversize`), the request is unaffected.
- A `route_index` read that hangs costs at most min(1 s, half of the time left) before the build starts; with a cold tree (the 4.5 s case) that request 503s exactly as before. This is the price of bounding the read, stated in the endpoint doc.
- The persisted-hit path repeats the four fingerprint reads the router already does for its result cache. It only runs on a cold or expired (60 s) in-memory index, so the duplicate is one extra small read set per minute per tenant at most.
- The existing test "ISS-427 every Mongo read of a /route call carries maxTimeMS" had to exclude `replaceOne` (a write, not a read). Not weakened for reads: the loop still asserts `maxTimeMS` on every `find`/`findOne`, including the new `route_index` and `tree_index` reads.
