## Open points (declared, not defects)
1. **Reachability under the real `sessionVisible`.** `knowledge.ts:200` makes `sessionVisible` false for every `whatsapp-batch` source, so with the real visibility object a WhatsApp session is already excluded from the step B frontier, live or not. The C1 and C2 tests therefore inject a link-blind `sessionVisible` for that one session, as checker B's repro implied. The H-14 gate must not depend on that unrelated clause, and the issue records the leak as reproduced, so the per-request link check is the fix; whether the leak is reachable in production today is for the checker to weigh.
2. **Option (a) not taken.** `visibilityFingerprint` still never reads `whatsapp_links`, so the persisted `route_index` and the `/search` result cache are still stamped without link state. For `/route` this is harmless because step B re-checks per request; for `/search`, WhatsApp-session results are never cached (`waSessions`) and no external model is involved. If the checker wants rotation as well, it is one more entry in the `Promise.all` and an update of the pinned `calls.length === 4`.
3. **Step B latency.** The gate adds per-session point reads before each step B call (only when step A is unsure). Memoised per request, deadline-bounded. Not measured against production data.
4. **Fail closed is per session on a timeout.** When the eligibility reads exceed half the remaining budget, the unverified sessions are dropped from the frontier and the request continues with whatever was verified (possibly an empty frontier, which becomes `llmFailed` and falls back to step A). It does not return an error.
5. **Out of scope and untouched:** ISS-WARLG-002 (live/state allowlist hardening) and ISS-WARLG-003 (stale comments). `/ask` and the hydrators were not changed. Consent (D-210): no consent code was read for, modified, extended or relied on; the revoke/unlink consent follow-through is not part of this fix.
