## Flags for the coordinator and checker
- **Loopback-mongod clauses are MEASURED** (C3A-C3 index, C3A-C6 20-parallel create, C3A-C8 two-process lease, the SIGKILL part of C3A-C8c, the Mongo half of C3A-I6) on a mongod 7.0.24 the builder started on 127.0.0.1 from the already cached binary (no download, no node_modules copy). Still NOT-MEASURED: a graceful SIGTERM on Windows (shutdown order is proven in-process by "C3A-C8e") and any behaviour on a replica set or Atlas (the lease uses no transaction, so none is claimed).
- **Contract tension (resolved).** The contract allows a loopback mongod; the first brief forbade any real Mongo connection, so the clauses were first reported NOT-MEASURED. A later instruction allowed a self-started loopback mongod; the clauses were then measured. Two defects were in the TEST, not the code: the lease-child processes each picked their own random database (so both always won) and the winner was expected to open exactly one socket while the child opened two. Fixed in `src/api/svc.test.ts` only; production source is unchanged since d6935956.
- **Merge gate (contract):** a PASS does not authorise merging; D-023's two open readings wait for the Approver.
- **C3A-I2 dev-mode coverage is thin.** The existing six suites pass and the dev branch of `createServer` is unchanged in meaning, but no test drives the dev app over HTTP (its construction touches the database). A checker wanting that needs a loopback mongod.
- **Timing.** Fail closed is 0.5-1.0 s under tsx after the dynamic-import change (it was 12.8 s before); listen under tsx is about 2.6 s cold. These are tsx numbers; the compiled `node dist/index.js` is faster.
- **Windows SIGTERM.** The spawn test cannot deliver a graceful SIGTERM on Windows (`child.kill()` is a hard kill), so shutdown order is proven in-process by "C3A-C8e", not by a signalled child. The SIGTERM exit-0 and lease-release-then-exit path across a real signal is not measured here.
- **A GET carrying a body.** `GET /svc/v1/owners/{id}/session` with a JSON body is read and ignored; one variant was answered by Node's parser with a bare 400 in the test client (chunked GET). It cannot carry an owner id into a call (a GET never reads one), so C3A-C4a skips that variant. Follow-up: a raw-socket probe against the stubbed handler shows a chunked or content-length GET body now reaches the handler (415 / 404 with the envelope); the bare `400 Bad Request` came from Node's default answer on a server with no `clientError` listener (the test harness server). The real server wires `svcClientError` (src/api/server.ts:168), which answers a parser-level error with the envelope. A test wires `svcClientError` onto its own server and checks the envelope (src/api/svc.test.ts around line 556); that `server.ts:168` does the same wiring on the real server is by reading, not by a test.
- **A refused oversized body.** The server answers 413 and drains at most about 124 KiB of that request, then closes; a client still sending past that sees a reset, by design (C3A-C2d bound).
- **Lease clock.** Expiry uses the local process clock (D-023 [ASSUMPTION], TTL 60 s, renew 20 s).
- **Defects found outside the unit:** the existing `mongo.ts` connect log printed the full connection string (credentials included); fixed in passing (logs host and database only, `safeUriHost`). The connected log line printed the full phone number; it now logs the two-digit hint.

- **Interpretations in the review repairs.** (R1) A level-`warn` child logger also drops Baileys' own `info` and `debug` lines that are not about the account; a `warn` or `error` from Baileys that happens to carry a number would still be written. (R2) A failed start of a session that was `logged_out` returns it to `logged_out` with its old detail, not to absent. (R3) A `freeze` alone leaves an in-flight session registered as `connecting` with no socket; `stopAll` (the lease-lost and shutdown handlers always call it) removes it. If the two overlap, the later `rename` can fail with ENOENT and the unlink answers a 5xx; the owner is already marked unlinked and a repeat of the call finishes it. Nothing is lost either way. `authState.ts` is not touched.
