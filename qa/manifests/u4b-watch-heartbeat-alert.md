## A second, independent new-file question: the detector's invocation

Per the brief: "A separate check that reads it and alerts... It must be a *different* code path
from the writer — a detector that only runs inside the thing it monitors cannot detect that thing
not running." `scripts/watch/run-watch.mjs` is invoked as a one-shot script (no evidence in this
repo of a daemon wrapping it — `docs/plan.md`/`docs/meeting-bot-roadmap.md` have no cron/Task
Scheduler entry naming it; U6's Task Scheduler work, which *does* install scheduled tasks, is
gated behind `qa/gates/live-recording-proof-method.md` per D-046 and is not part of this unit). A
check placed anywhere inside `run-watch.mjs` itself — even a function never called from `main()`'s
own execution — still only runs when something invokes that script, which is precisely the failure
mode R2 exists for (a script that stops being invoked at all looks identical to one that ran and
found nothing wrong).

The one candidate I found that is a **genuinely separate, already-running process**:
`apps/api/src/routes/health.ts` (`GET /health`, unauthenticated, already does a db ping + real
per-collection counts on every request — the exact shape a heartbeat-staleness check would extend).
`apps/api` runs as a long-lived server, independent of whatever schedules `run-watch.mjs`; if the
watcher's scheduled invocation dies, the API process keeps running and a periodic timer or an
external monitor hitting `/health` would still see it. This is an **existing file** I could extend
in place — but doing so still requires reading `watch_heartbeat` rows, which needs the same missing
`packages/db/src/collections/watch-heartbeat.ts` accessor. So this half is blocked by the same gate
as the write side, not a second independent blocker — flagging it here so the HUMAN_GATE answer can
cover both at once (see "HUMAN_GATE" section below) rather than needing a second round-trip.

I am **not** proposing a new scheduled task (a fifth new-file-equivalent, and squarely U6's
territory, which D-046 explicitly keeps gated pending the live-recording proof).

## Definition of "completed run" (per the brief's explicit ask)

A phase is "completed" the moment its own `try { ... } catch { ... }` block in `main()` finishes —
**whether it succeeded or caught and logged an error into `errors[]`.** `run-watch.mjs`'s three
phases (Drive listing, Gmail scan, calendar parse) each already wrap their real work in exactly such
a block and never let a phase-level error escape `main()` — a poll that fails still returns control
to the loop, which is R1's whole territory (a poll ran and found a problem). What R2 must catch is
different: the process not reaching the end of a phase's try/catch **at all** — an uncaught
exception past that boundary, an infinite loop/hang (the actual Ashoka failure mode — no evidence a
`--ingest` run over-runs any timeout), or the process being killed. `buildHeartbeatDoc`'s doc
comment names the exact three drop-in points (end of steps 1/2/3 in `main()`) this would attach to.
Each phase gets its **own** heartbeat rather than one heartbeat for the whole run, so a hang in
(say) the Gmail phase doesn't retroactively make Drive's already-completed, already-healthy phase
look stale too — the granular signal is strictly more informative than a single per-tenant row.

**Committed** (in the two files this unit is authorized to edit): `notifyWatchSilent`'s 4 new tests

**Not committed, verified by direct exercise** (same reason U4a's `shouldAlertPollFailed`/

  a stale timestamp, per the brief's explicit ask.
- **heartbeat exactly at the boundary** (`now - last === intervalMs`) → **not** stale (`false`).
  **one ms past the boundary** → stale (`true`). Confirms the strict-inequality semantics above.
- **fresh heartbeat** (1s old against a 2h interval) → not stale.
- **multiple sources, one stale, others fresh** — `findStaleHeartbeats` over three rows (drive

- **a resumed run clears the state** — re-evaluating a fresh heartbeat after a stale one for the
  same function call returns `false`; since `isHeartbeatStale` is a pure function of its inputs
  (not a stored flag), "clearing" is definitionally automatic — there is no separate state to reset,
  which is worth stating plainly since a naive stateful implementation could get this wrong and this
  one cannot.
- **the detector firing when the writer is not running at all** — this is the one claim in the
  brief's test list that these pure-function tests **cannot** prove, by construction: a unit test
  calls the function, which is itself "the writer running." Proving this needs the detector actually
  invoked from a separate process (the `health.ts` extension proposed above) polling real Mongo
  state while `run-watch.mjs` is not running — not reachable without the collection. Named plainly
  rather than claimed.
