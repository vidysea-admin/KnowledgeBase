## Scope
Touches only `packages/core/src/job-queue/` (+ this manifest and the lane ledger). `core/index.ts` and `run-state-store/` untouched.
- `queue-lock.ts`: two additions to the judge, both only for a lock whose holder pid answers, whose age is >= `staleMs` (30 s) and whose token is not a nested same-thread holder. Everything else is unchanged: ESRCH/EPERM probe, 30 s unverifiable rule, 1 h ceiling, claim-then-rename takeover, token re-check before the rename, EPERM/EBUSY/EACCES contention handling, typed `conflict` with nothing written.
  1. PID REUSE (identity beyond pid): the OS start time of the live pid is compared with the `at` the holder wrote into the lock; a process that started more than 1 s AFTER the lock was written cannot be the holder, so the lock is taken over at once. New `defaultQueueStartTime(pid)`: own pid = `Date.now()-process.uptime()`, Linux = `/proc/<pid>/stat` + `btime`, macOS = `ps -o lstart=`, Windows = one `powershell.exe Get-Process -Id N` spawn (5 s timeout, no native deps). Unavailable / throws / NaN = unknown = no displacement (old 1 h rule). The lookup is lazy (only for a lock >= 30 s old, i.e. never on the hot path) and cached per call and pid.
  2. DEAD WORKER THREAD (lease): the lock body already records `thread` (worker_threads id). A holder with thread id > 0 that has held the lock for `threadLeaseMs` (default 60 s, `QUEUE_LOCK_THREAD_LEASE_MS`) is presumed dead and taken over. A main-thread holder (id 0) or a legacy body (no thread) is not leased: the main thread cannot die while its pid lives, so those keep the full 1 h protection, which is what keeps ISS-JOBQLOST-003 closed for processes.
- `file-job-queue.ts`: two optional seams `lockThreadLeaseMs`, `lockStartTime` (production leaves them unset). When a test injects `lockIsAlive` (fake pids) and no `lockStartTime`, the start-time source defaults to "unknown" so fake pids never hit the real process table.
- Tests: NEW `file-job-queue.pid-reuse.test.ts` (8) + `file-job-queue.dead-thread.worker.ts` (worker used by the S5 test). ONE EXISTING TEST CHANGED on purpose: in `file-job-queue.stalled-holder.test.ts` "another THREAD of this process ..." previously asserted a worker-thread holder aged 10 x staleMs (300 s) is never displaced; that is exactly the behaviour ISS-JOBQSTALL-002 asks to change, so the age is now `lease - 1` (still refused) and the displacement past the lease is asserted in the new file. Nothing else in the 7 existing test files was touched.

## Why this design (and not the other)
- Heartbeat/lease for every holder was rejected: the critical section is synchronous (`Atomics.wait` sleeps, sync fs), so no timer can run inside it and a "heartbeat" would only be the lock's age. A rule "age >= bound = stale even if the pid answers" is exactly the old age-only takeover that ISS-JOBQLOST-003 removed (holder stalled 31 s, displaced, both write), and it would fail the recorded reproduction and the checker's real-process replay at +31 s and +59 min.
- Start-time identity is exact for the case it covers (a pid can only be reused by a process born after the old one died, hence after the lock was written), needs nothing from the holder, and works on locks already on disk. Cost measured on this Windows Server 2025 box: 310-475 ms per foreign-pid lookup (Get-Process via powershell.exe), paid at most once per queue call and only when a lock is already >= 30 s old; own pid is free.
- Threads share the pid and start time, so identity cannot help; the only available signal is how long the holder has held the lock. I applied the lease ONLY to holders that record a worker-thread id, so the process/main-thread stalled-holder guarantee of ISS-JOBQLOST-003 is untouched. If a live worker thread is itself blocked inside the critical section longer than the lease, it is indistinguishable from a dead one and is displaced; the token + content re-check right before its rename then makes it return `conflict` and write nothing, except in the same post-check window as ISS-JOBQSTALL-001 (filed ISS-JOBQPID-001, low).

## Guarantee now given, exactly
A queue lock whose holder died because its pid was reused by a later process (when the OS start time is obtainable) or because its worker thread was terminated no longer blocks writers for up to 1 h: it is taken over once it is 30 s old (reused pid) or 60 s old (worker thread), while a live main-thread or other-process holder is still never displaced before 1 h and a writer that loses the lock still gets the typed `conflict` and writes nothing.

## Residual window, exactly
A live worker thread blocked inside the critical section for more than 60 s is displaced like a dead one and, if it then resumes between its last ownership check and its rename, can overwrite the displacer's acknowledged write (ISS-JOBQPID-001, same window as ISS-JOBQSTALL-001); pid reuse is not detected when the start time cannot be read, within 30 s of the lock being written, or within 1 s of it (ISS-JOBQPID-002).
