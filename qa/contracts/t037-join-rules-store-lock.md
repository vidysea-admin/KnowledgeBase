# Contract — t037-join-rules-store-lock (T-037, store concurrency slice)

> Ground truth for `packages/meeting-bot/src/calendar/join-rules-store.ts` and `join-rules-store-lock.ts`. Written by the checker; the maker never edits it.
> Extends `qa/contracts/t037-join-rules-persistence.md` (its criteria 1-4 still hold). Security class, uncapped.

## Security property
An acknowledged write (a call that returned without throwing) is never lost: not by a concurrent process, not by a crash, not by a reader. A write that did not happen throws a `JoinRulesStoreError`. The rules file is never missing, truncated or partial after any failure, and a reader sees either the previous or the new complete, valid document. (A missing file reads as "no rules", so a deleted-then-failed rename would silently turn a tenant's refusals into joins.)

## Criteria
1. **Mutual exclusion across processes.** `saveJoinRules`, `recordTenantApproval` and `recordTenantOptOut` hold an exclusive per-tenant lock `<stateDir>/join-rules/<tenant>.lock` (created with `wx`) around the whole read-validate-modify-write. N real processes recording distinct entries for one tenant, with no test hook, end with exactly the acknowledged entries present, a document that passes the engine validators, and no `.lock` or `.tmp` left.
2. **Failure is loud and clean.** Lock wait exceeded -> `JoinRulesStoreError` `locked`, nothing written, the other holder's lock untouched. A hard create failure -> `lock-failed`. The lock is released in a `finally` after success, validation error, refused load and failed rename. A call that throws left no entry in the file.
3. **Tenants are independent.** Contention on one tenant does not delay or fail writes to another.
4. **No stealing.** A lock older than the stale threshold (default 30 s; from the `at` stamp, else mtime) is reported with its path, age, content and the manual step (confirm the pid is gone, delete that file, retry) and is never removed by the store. Garbage, empty, array or `null` lock content produces only `locked`, never another error type. Manual deletion restores service.
5. **Lock path safety.** The lock file name is derived only from the validated tenant id; nothing outside `<stateDir>/join-rules/` can be created or deleted.
6. **Rename retry.** A rename that fails with EPERM/EACCES/EBUSY is retried for at most ~3 s under the lock. On exhaustion or any other rename error: `write-failed`, temp file removed, ORIGINAL file byte-identical. The target is never unlinked, truncated or renamed away at any point (no delete-then-rename).
7. **Readers.** `loadJoinRules` takes no lock. During concurrent writes every read returns a valid complete document or throws a clean store error; it never returns "no rules" for a tenant that has rules, and never exposes a temp file or partial write.
8. **Overwrite protection.** `saveJoinRules` refuses by default an existing file that is unreadable, corrupt, oversized, schema-invalid or embeds another tenant (the load error is thrown, nothing written); a non-regular file is refused always; `{overwriteInvalid: true}` replaces it. The record helpers cannot be given `overwriteInvalid`.
9. **API compatibility.** Public functions stay synchronous; existing error codes keep their meaning; added codes are only `locked` and `lock-failed`; the signature gains only trailing optional options, so `(dir, tenant, value)` callers are unaffected.
10. **Test-only hooks unreachable in production.** `afterRead` and `rename` exist only as per-call option fields; no environment variable or default turns either on.
11. **Operator recovery (precondition for unattended wiring, not for this unit).** A holder killed while holding the lock blocks all writes for that tenant, including opt-outs, until a human deletes the lock. The service must either alert on `locked`/stale errors with the runbook, or the store must recover automatically (see ISS-T037LOCK-001).
12. **Tests.** Cover 1-8 with real processes. Mutations that must fail the suite: no lock acquisition, lock opened without `wx`, stale-lock stealing, rename failure swallowed, load-first refusal skipped, target deleted before rename.

## Stale-lock takeover (added by checker, unit `t037-join-rules-stale-lock-takeover`, cycle 0). Supersedes criteria 4 and 11 where they conflict
**Guarantee G1 (outranks recovery):** at most ONE process believes it holds a tenant's lock at any instant, and a data rename is performed only by the believer. Recovery of a dead holder's lock is secondary: when in doubt the lock stays `locked`.
**Takeover rule:** a lock may be replaced only if ALL hold: (a) content parses strictly (token `[A-Za-z0-9-]{1,64}`, positive safe-integer pid, non-empty host, size <= 4096); (b) host equals this machine's hostname (exact); (c) the OS reports ESRCH for the pid (EPERM, any other error, pid <= 0 or non-integer = alive/unknown, keep); (d) the lock has existed for longer than `staleMs` (an ADDITIONAL conjunct: it can only remove takeovers, and it bounds the damage when (c) is wrong); (e) the removal step never leaves a window in which a lock that is NOT the one judged dead is absent (no "rename away, check, link back": a live lock must never be moved).
**Deployment preconditions (must be stated by any host wiring this store):**
 P1. One PID namespace per lock directory. Two processes sharing a state directory from different PID namespaces (separate containers started with equal `--hostname`/`--uts host`, a container and the host, WSL and Windows, anything where `kill(pid,0)` cannot see the holder) will see a live holder as ESRCH. Rule (b) only protects when hostnames differ. This is an unsupported deployment; the host must refuse to start otherwise.
 P2. The state directory must support hard links (`fs.link`); where it does not, takeover is disabled (lock stays `locked`) and the operator runbook applies. Never fall back to delete-and-create.
 P3. A recycled pid keeps a dead holder's lock alive (fail safe); the operator runbook applies.
**Required properties of the takeover protocol (tested by interleaving, not by one fixed order):** with N >= 3 contenders (takers and plain acquirers) and a dead lock older than `staleMs`, over every sampled ordering of the protocol's file operations: no two contenders hold the lock at once; no data rename by a non-holder; no lock file left that nobody owns once all contenders finished; a tombstone/claim marker left by a crashed taker delays only that lock and expires on a clock that is NOT the dead lock's own mtime (a hard link shares the lock's inode, so its mtime is the lock's age, not the claim's).
**Tests that must exist:** an N-process (>=3) takeover race against a dead lock aged beyond `staleMs`, with the claim-expiry path exercised; a link-failure (EPERM/ENOTSUP/EXDEV) case asserting `locked`, lock bytes untouched; a probe-lies case that documents the residual and fails if the age conjunct (d) is removed.

## Stale-lock takeover: cycle-1 amendments (checker, claim-then-rename design, commit 5a764db). These supersede the cycle-0 text above where they conflict
**Protocol under contract:** judge (strict parse, exact-case host, recorded age > `staleMs`, pid ESRCH) -> claim (`wx` create of `<lock>.claim.<deadToken>` holding the CLAIMANT's own body) -> reread (lock bytes identical to the bytes judged, pid re-probed, age re-checked) -> `rename(claim, lock)` (one atomic step: there is never an instant without a lock file) -> verify own token. `save` re-checks ownership immediately before its data rename; release verifies the token. No `link`, no moved lock.
**Preconditions (the host wiring MUST state them; P2 is obsolete because no hard link remains):**
 P1 (strengthened). Exactly ONE PID namespace and ONE hostname per lock directory, and the liveness probe must be truthful. If a LIVE holder is reported dead (containers with equal `--hostname`/`--uts host`, WSL vs Windows, anything where `kill(pid,0)` cannot see the holder) AND its lock is older than `staleMs`, the takeover proceeds and **writes can be lost**: measured by the checker with a lying probe and a holder that is slow by more than `staleMs`: two believers in 28% of orderings, a data rename by a non-holder in 15%, an acknowledged write missing from the final file in 2.1%, and the old holder's release unlinking the NEW holder's lock in 14% (read-then-unlink gap), after which a third process can acquire. A lock younger than `staleMs` was safe in 100,000 of 100,000 orderings. The host must refuse to start when it cannot guarantee P1.
 P3. A recycled pid keeps a dead holder's lock alive (fail safe, manual recovery).
 P4 (new, operator rule). While ANY process may still be using a state directory, an operator must NOT delete or rename a join-rules `.lock` file by hand. A deletion that lands in the one-syscall gap between a taker's re-read and its rename, with a third process creating a new lock there, makes the taker replace that NEW live lock (ISS-LOCKTAKE-007; measured 1.7% of orderings with a deletion scheduled at a step boundary, 0.06% ending in a lost acknowledged write; in reality a gap of microseconds). Procedure for a lock that is `locked` and stale: stop every writer of that state directory first (or confirm none is running), then delete the lock, then start them again.
 P5 (new, abandoned-claim recovery). A takeover claim `<lock>.claim.<deadToken>` is NEVER removed automatically; it blocks takeover of THAT dead token only (a later dead lock has another token and another claim name), and does not block a normal acquire once the lock file is gone. It is left behind only if the claimant is killed inside the few-syscall window between claim and rename, or if a claim write / claim unlink fails (ISS-LOCKTAKE-008). Recovery while the service runs: read the claimant's pid from the claim file; if that process is gone, delete ONLY the claim file (never the lock): the next acquirer then completes the takeover safely. Deleting a claim whose claimant is alive can let a second taker in and is forbidden. An empty claim file is a failed claim write: it is safe to delete once no writer is mid-acquire.
**Required properties (verified at cycle 1):** over every sampled ordering of the protocol's file operations with 2-3 takers, a late normal acquirer, the dead holder's late release/save and a second tenant in the same directory: at most one believer; the lock file never absent without a legal removal (release or operator); no data rename by a non-believer; no live lock or foreign claim removed; no free-but-unacquirable state. Abandoned-claim EXPIRY is no longer required (cycle-0 wording withdrawn: the maker's manual-recovery policy P5 is accepted because the window is microseconds, the failure is fail-safe and a recursive claim-on-claim protocol on a data-write path costs more than it buys).
**Clock:** a lock whose recorded time is in the future (clock stepped back, hostile stamp) is never "old": takeover is delayed until the clock passes `at + staleMs` (bounded by the size of the step); a recorded time far in the past never causes a takeover without the pid probe saying ESRCH (conjunction, never disjunction).
**Messages:** the `locked` message names lock and claim paths for the operator log only; the API maps `locked` to a fixed 503 body and must keep doing so (a path in an HTTP response is a finding).
