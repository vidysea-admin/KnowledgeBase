## Acceptance

- **C1 Usable authenticated intake and ownership.** A mounted API/worker or documented executable production path accepts a bounded, typed operation from a verified tenant/actor and returns a stable operation ID. Tenant/actor/permission come from authenticated server state, never caller identity fields. Unknown operation kinds, extra fields, malformed payloads, foreign IDs and insufficient scopes fail closed before writes. Wider form/application operations have an explicit registered operation type and validation path; an arbitrary shell, URL, browser script or model-generated action is not an approved handler. The intake, status and operator intervention paths are usable consumers, not test-only dependency wiring.
- **C2 Durable state and replay.** Intake persists tenant-scoped natural identity, operation kind/version, validated payload or protected reference, creation/update times, execution state, attempt limit and history/outcome. Reconstructing the store/runtime preserves queued, running, waiting-for-operator, succeeded and terminal-failed states actually claimed by the implementation. Same-tenant replay with the same idempotency key and same payload returns the existing operation without duplicate side effects; conflicting reuse is refused. Different tenants cannot collide or observe each other's keys, payloads or state. Missing/corrupt storage and failed writes are reported honestly, never successful empty or in-memory-only durability.
- **C3 Exclusive execution and stale-owner recovery.** A real runtime consumer claims eligible work atomically with a bounded lease/owner token and updates it using that token. Concurrent workers cannot both execute the same operation under a valid lease; a stale worker cannot complete, heartbeat or overwrite a reassigned operation. Crash/restart/stale-lease behavior is tested with a controllable clock and a fresh runtime/store. Recovery is bounded by attempts and does not silently abandon work. Terminal or waiting-for-operator operations are not automatically rerun.
- **C4 Side effects, limits and idempotency.** At least one explicitly allowed routine flows through intake → persisted claim → registered bounded handler → durable result → status/monitor consumer. Timeouts, handler errors, cancellation and malformed results cannot fabricate success. Every side-effect adapter has a stable operation identity and a documented duplicate/crash guarantee: a side effect committed before outcome persistence must be deduplicated by the adapter or parked for operator reconciliation. Blind retry is unacceptable where duplicate application submission, payment, message or other irreversible action is possible. Handler selection, credentials and destination are trusted runtime configuration; intake cannot replace them. Execution produces no arbitrary command injection, SSRF or unapproved network action.
- **C5 Bot monitoring and exception handoff.** A callable production monitor consumes persisted operations and detects the submitted failure/stall conditions from recorded evidence and heartbeat timestamps. It writes a durable, tenant-scoped intervention or notification with stable identity and a concrete reason/action; repeated scans do not create duplicate incidents or repeat completed remediation. A stale/failing dependency is shown as unavailable rather than healthy. Safe automatic remediation is limited to registered authorized actions and bounded retry; unknown, ambiguous or irreversible situations enter waiting-for-operator. Sanitized status distinguishes queued/running/recovered/waiting/failed/succeeded, and downstream consumers expose the operator action required.
- **C6 Protected recovery and audit.** Operator retry/resume/cancel/reconcile requires verified permission and current state/version; cross-tenant and stale requests refuse without mutation. A lower-privilege actor cannot approve its own unknown handler or privileged action. State transitions and intervention decisions retain actor/owner, operation, outcome and timestamp without credentials or unnecessary personal form data. Failed audit/history/state persistence cannot acknowledge a mutation as successful. Payload/status/error/notification projections cannot leak another tenant, raw credentials, form PII, access links or arbitrary upstream exception text. Retention/deletion and privileged permission updates reuse their own authorization boundaries.
- **C7 Sample, consumer and failure proof.** A bounded isolated fixture exercises the actual mounted/callable runtime and immediate consumer: authenticated intake; duplicate/conflicting intake; execution; monitor observation; failure or stale lease; durable handoff; authorized recovery; fresh-store/runtime read/replay. Include at least two tenants, concurrency/stale-owner refusal, write failure, a crash after side effect before commit, handler timeout and exhausted retries for claimed paths. Source review covers runtime composition, durable store and downstream consumer. Required contracts/verify_contracts.py evidence is retained. In-memory adapters can support probes, but cannot establish production persistence or claim ownership alone.
- **C8 Explicit whole-task gates.** The manifest states exactly which registered operation types, runtime entry points, durability/duplicate guarantees and operator paths are delivered, and which catalogue requirements remain. Implementation authorization D-170 is not authorization to submit real student applications, send external messages/email/Telegram, expose/export form data, perform payments, mutate production, activate OS supervisors/schedules, deploy, or run unattended live operations. Any such activation needs the existing explicit approval/account/host gate and actual evidence. Local injected side effects are labeled as fixtures. No live bot-monitoring, production recovery, deployment or completion claim is inferred from primitive tests, stale evidence, flags, documentation or human gates.
- **C9 Approved form executor and grounded authority.** Remaining F1 implementation includes a registered actual form/routine execution adapter with a mounted production composition path; checklist/readiness controls alone cannot close this scope. Execution requires a durable approval bound to the exact validated operation payload, trusted target/destination and credential generation, as well as the canonical source document revision/hash and cited span/value authority for every claimed grounded field. Missing/changed source, stale payload/target approval, wrong tenant, forbidden current HostingService role or unavailable authority dependency refuses before adapter side effects. A durable uncertain intent is committed before the side-effect adapter is invoked. Unsafe ambiguous work remains parked and cannot be blindly retried/cancelled. Reconciliation succeeds only using adapter-verified evidence for the exact tenant/operation, with truthful durable outcome and audit; a caller receipt, checklist result or operator assertion alone cannot establish submission success. Safe retries use the same stable adapter operation ID and preserve uncertainty until a verified receipt establishes the result. Focused evidence includes approval staleness/revocation, source mutation, trusted target mutation, concurrent claim and stale-owner refusal, failed intent/commit persistence, crash ambiguity, forged/mismatched receipt, and fresh-store/runtime consumer replay. Build-time adapter fixtures exercise this real interface without contacting a target; they do not establish live form submission or deployment acceptance.

## Packet and verdict gate

Maker provides one agreed manifest/packet at `Status: ready-for-check`, its exact slug and Fix cycle, changed-file and caller/consumer map, final SHA-256 hashes, bounded commands with duration/exit/output artifacts, fixtures, error boundaries and remaining gates. The independent checker verifies current bytes/cycle and derives a focused behavioral probe under root's CPU lease; no full suites, browsers, providers, production targets or external messages are permitted in this focused check.

PASS certifies complete acceptance of the explicitly submitted authorized unit, with every excluded umbrella requirement named as remaining. HOLD applies to missing packet/provenance, changing candidate, missing mounted consumer/durable dependency or blocked required evidence; a demonstrated criterion violation is FAIL. A narrower preparatory unit may PASS its named scope without closing T-061. Only the checker writes the matching verdict; maker closes out only the same cycle and hashes after independent PASS.
