## Criteria
- **[B10-C1]** One failure alert per failed capture. Capture X ends `failed`. Over at least 4 scheduler ticks (including `tick()` replays, `lifecycle-alerts.mjs:127`) and one retry of X that fails again (`attempts` below 3, `scripts/webinar/scheduler/dispatch.mjs:26,31`), the sender is called exactly once with a failure-kind alert (`capture-failed`) for X, to the one configured recipient. A second failed capture Y adds exactly one more. Negative cases, each with zero failure alerts: captures only `queued`, `recording`, `processing`, or `ready` (a `ready` capture still sends its `capture-done` mail as today; the test counts failure-kind alerts and names the others separately); email off or no valid recipient (zero sender calls, no throw, the row stays `failed`).
- **[B10-C2]** The reason lookup. A reason matches a listed name when it equals the name, or starts with the name followed by one ASCII character that is not a letter, digit, underscore or hyphen (checker-narrowed 2026-11-25: the hyphen does not end a name, because the listed names contain hyphens). Positives: every name in the set, each exactly as before (and each still gives its own entry's detail); `admission_denied`; `admission_denied: free text`; `admission_denied - free text` (the space ends the name). Negatives, each giving the neutral line: `admission_denied_extra`, `admission_deniedx`, `admission_denied2`, `xadmission_denied`, `the host said admission_denied later`, `admission` (a prefix of the name), `` (empty), `admission_denied-x`, and the hyphen-suffixed look-alikes of the old names, including the real value `rescheduled-completed` (written at `packages/meeting-bot/src/calendar/auto-record-policy.ts:144`), `cancelled-by-host` and `retry-limit-reached`, each of which must give the neutral line and never the shorter name's entry, `admission_denied\u00e9` (checker-added: a non-ASCII letter after the name is a word character, so only a non-letter, non-digit, non-underscore ASCII character, or the end of the string, ends the name). Every reason that matched before still matches the same entry (test: the old exact-match result and the new result agree on every name in the set).
- **[B10-C3]** Content. The detail line for a match is `Coverage: <the matched name>.`, never the whole reason: `admission_denied: <fake secret>` gives `Coverage: admission_denied.`. The decoded mail names the event (`capture-failed` or its label "Recording FAILED"); the capture is identified in the mail by its title and scheduled time as every alert mail does today, and the capture id (`sessionKey`) is asserted at the sender boundary, as the `sessionKey` of the alert input handed to `raise`, not in the decoded text (checker-corrected 2026-11-25: the contract assumed `describeAlert` and `buildRawEmail` print `sessionKey`; the checker read `alerts.ts:describeAlert` and `gws-channels.ts:buildRawEmail` and they do not, and both files are byte-equal-to-HEAD under B10-I1; the id still reaches the dashboard feed event). [SECURITY CLASS: credential handling (checker-tagged)] A failing capture whose reason and environment carry fake secrets (a fake API key, a fake Telegram token, a join URL with `?pwd=...`, a fake passcode sentence, a fake transcript sentence, text after the name in the reason) yields a mail in which NONE of those strings appears, and a title that carries a join URL with `?pwd=...` appears only as `[link removed]` (`cleanBotText` removes URLs, `bot-events.ts:34`). The assertion is on the decoded text, not on the stub's arguments. (checker-changed: the maker's line also listed the TITLE among the fields whose fake secrets must be absent. That cannot be proved inside the unit's files. The title is mailed today by design: `alerts.ts:116` and `:197` put `cleanBotText(title, ...)` in the body and the subject, and `cleanBotText` strips URLs and control characters only; `alerts.ts` is not editable here (B10-I1), and dropping the title would change the mail for every alert kind. So for the title the criterion is: no URL survives (the `?pwd=` case), and the title is rendered exactly as today. A non-URL secret typed into a meeting title therefore still reaches the mail; that is existing behaviour, not made worse by this unit, and is recorded under Out of scope for the owner.)
- **[B10-C4]** End to end, child to mail. A fake child (the launcher takes an injectable `spawnLike`, `reconnect-gaps.ts:125`; no real browser) that writes `lkb capture failed: admission_denied: <anything>` to stderr and exits non-zero makes the launcher reject with the message `admission_denied: Recording pipeline exited <code>`; run through the scheduler's capture path (`dispatch.mjs:124`) the failed row's `reason` starts with `admission_denied:`; and exactly one failure alert goes out whose decoded text names `admission_denied` (the capture id is asserted on the alert input handed to `raise`, as in B10-C3). A child that exits non-zero with no matching stderr line gives the unchanged message `Recording pipeline exited <code>` and exactly one mail with the neutral line.
- **[B10-C5]** A failing sender changes nothing else. With a sender that (a) throws, (b) exits non-zero, (c) hangs longer than the 30 s `gws` timeout (`gws-channels.ts:21`): the row's `status` and `reason` stay as the capture left them; the tick returns (the final `await notifications.wait(); await alerts.wait()` at `scripts/webinar/run-pipeline.mjs:261` is bounded: by the existing retry code, which this unit may not change (`alerts.ts`, `gws-channels.ts`, `run-pipeline.mjs`) and which makes at most 3 attempts of the 30 s `gws` timeout per capture and kind, so at most 3 x 30 s = 90 s in total and, measured by the builder on a fake clock, 2 attempts = 60 s in one tick (checker-amended 2026-11-25: the earlier "under 35 s" presumed one send attempt per tick, which the checker note below already flagged as possibly unprovable; the test must assert the 3-attempt / 90 s ceiling and report the measured number)); the next due capture is still dispatched; the log line carries no secret; (checker note: the 35 s bound presumes one send attempt per tick. If the existing retry code runs its up to 3 attempts inside one `alerts.wait()`, the measured bound is about 3 x 30 s, and the builder reports the measured number; making it smaller needs `alerts.ts`, `gws-channels.ts` or `run-pipeline.mjs`, none of which this unit may edit, so that is a STOP and a question, not a quiet edit.) delivery is retried at most 3 times per capture and kind (`MAX_ATTEMPTS`, `alerts.ts:36`), then stops. A sender that fails twice and then works gives exactly one mail in the end.
- **[B10-C6]** Telegram and `notifyOperation` unchanged. The diff has no change to `run-pipeline-deps.mjs:85-94` or `telegram-channel.ts`. With Telegram unset `notifyOperation` returns `'disabled'` and calls no sender; with `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID` set (fake values, the channel's `send` replaced; never `api.telegram.org`) it sends the same text as today (`Webinar <id>: <status> (<reason>). Check the operations view for details.`) and returns `'sent'`. The existing tests (`scripts/webinar/run-pipeline.test.mjs:163-212`, `packages/meeting-bot/src/capture/notify/telegram-channel.test.ts:81`) pass unchanged (no existing assertion edited, removed or skipped). With Telegram set and email set, one failure gives one Telegram message and one mail; neither suppresses the other.
- **[B10-C7]** The stderr rule is narrow. With the same fake child: (a) `lkb capture failed: something_else: secret=abc` leaves the message unchanged, and neither `something_else` nor `secret=abc` appears in the row, in any log line the pipeline writes, or in the decoded mail; (b) `lkb capture failed: admission_denied_extra`, `admission_deniedx`, `admission_denied2` and `admission_denied-x` (hyphen is not a delimiter) do not match; `admission_denied` at the end of the line, and `admission_denied: x`, do; a line that only contains the name later (`error: lkb capture failed: admission_denied`, or `note admission_denied`) does not match; (c) the LAST line that starts with `lkb capture failed: ` decides: an `admission_denied` line followed by a `something_else` line gives the unchanged message, and the reverse order gives `admission_denied: ...`; (d) bounded read: a child that writes several megabytes to stderr (many lines, and one single line longer than the cap with no newline) neither blocks (stderr stays drained, the child exits, the launcher still settles) nor grows the retained text beyond a fixed cap [ASSUMPTION: about 64 KiB, as the stdout buffer at `reconnect-gaps.ts:144`], and a name that sits only beyond the cap is not kept (checker-clarified: the retained window is the MOST RECENT 64 KiB, exactly as the stdout buffer's `slice(-65536)` at `:144`, so that "the LAST line decides" in (c) is still honoured after a long stderr; a failure line that began before the window, or a single line longer than the window, is not kept); (e) the existing `reconnect-gaps.test.ts` cases (stop, privacy, control) pass unchanged and stdout lines still reach `onLine` as before.
