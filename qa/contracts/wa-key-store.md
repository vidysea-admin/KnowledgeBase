> Scope: `src/wa/authState.ts` and `src/wa/authState.test.ts` only. The database-backed store behind `createAuthState(userId)` (`src/wa/authState.ts:16`) and the four sibling functions `destroyAuthState` (`:45`), `hasRestorableAuthState` (`:83`), `restoreAuthState` (`:93`) and `linkedUserIds` (`:116`), selected by `config.keyStore`; the file store stays the development default and unchanged. Values are encrypted with AES-256-GCM, a fresh 12-byte nonce per value, under `config.keyEncryptionKey` (env `SESSION_KEYS_ENC_KEY`). Archived key sets are kept encrypted, the 5 newest per owner, each for at most `ARCHIVE_MAX_AGE_DAYS` (30) days, and are operator-only (D-025 item 1). It reads and writes through `waCreds()` and `waKeys()` (names above). The store is a thin per-key mirror of Baileys' `useMultiFileAuthState` (`node_modules/baileys/lib/Utils/use-multi-file-auth-state.js:28-120`): same key names, same `BufferJSON` encoding, same per-key semantics; `app-state-sync-key` values come back as `proto.Message.AppStateSyncKeyData` (`:96-98`). The test seam that lets one test body run against both backends is named in the manifest; the same test bodies also run on a throwaway loopback database where mongod is present (NOT-MEASURED for that part otherwise), and on an in-memory fake collection otherwise.

## Criteria
- **[C3B-C1]** Same behaviour as the file store, differentially. A seeded random sequence of 1000 operations (`keys.set` with a value, `keys.set` with `null`, `keys.get` of present and missing ids, across every key type below) runs on both stores and every returned value is equal between them (including the result for a missing id), and a plain-Map model agrees with both; the existing cases of `authState.test.ts` (archive instead of delete, restore, refuse to overwrite a live link, keep the newest archives, `linkedUserIds`) run as the same test bodies against both backends. A read through `makeCacheableSignalKeyStore` after a `set` or delete in the same handle never returns an older value.
  Check: `npx tsx --test src/wa/authState.test.ts`.
- **[C3B-C2]** Round trip of every value kind. For `creds` (with `Buffer` and nested binary fields, via `BufferJSON`) and for every key type, the value read back equals the value written byte for byte: `pre-key`, `session`, `sender-key`, `sender-key-memory`, `app-state-sync-key` (returned as `AppStateSyncKeyData`), `app-state-sync-version`, `lid-mapping`, `tctoken`, `device-list` and any other name in Baileys' `SignalDataTypeMap` (the manifest quotes that list from `node_modules/baileys/lib/Types/Auth.d.ts`; a type in the list that is not tested is a failure of this criterion). A write of `null` deletes the row.
  Check: `npx tsx --test src/wa/authState.test.ts`.
- **[C3B-C3]** At rest. Reading the raw backend rows (not through the store): no stored `value` contains the plaintext (a canary substring such as `CANARY-KEY-<random>` placed inside a key value and inside creds is absent from every raw field), `value` has the shape `{v: 1, nonce (12 bytes), ct, tag (16 bytes)}`, writing the same value twice stores two different nonces and two different `ct`, and the same value for two owners stores different `ct`. Only `_id`, `ownerUserId`, `archiveId`, `archivedAt`, `type`, `id` and `updatedAt` are plaintext (checker-tightened: the maker's list omitted `archivedAt`, which C3B-C8 requires on archived rows as a plain Date for the expiry index, and `_id`; no other plaintext field is allowed).
  Check: `npx tsx --test src/wa/authState.test.ts`.
- **[C3B-C4]** Wrong key, tampering and a missing key fail loudly, and are never "no key". (a) A store opened with a different 32-byte key rejects on read with a typed error; (b) flipping one byte of `ct`, `tag` or `nonce` rejects; (c) [ASSUMPTION: the owner, type and id are bound as additional authenticated data; accepted as a criterion by the checker because the failure it prevents, one owner's ciphertext being served as another's, is tenancy and credential handling] a valid ciphertext copied into another row (another owner, type or id) rejects; (d) when `creds` cannot be decrypted, `createAuthState` rejects: it never returns fresh `initAuthCreds()`, never overwrites or deletes the stored row, and a later correct-key open reads the original value; a key that cannot be decrypted is never returned as missing; (e) with `config.keyStore === 'mongo'` and no key, or a key not 32 bytes, `createAuthState` rejects: it never falls back to the file store or to plaintext; (f) no error message, log line or test output contains key bytes, a value or the canary.
  Check: `npx tsx --test src/wa/authState.test.ts`.
- **[C3B-C5]** Write-through, failed writes, concurrency. (a) After `await keys.set(...)` or `await saveCreds()` resolves, a second handle created on the same backend before the first is dropped reads the new value (no write-behind). (b) A backend that rejects the write makes `set` and `saveCreds` reject; the rejected value is not visible to a new handle and not served from the cache by the same handle; the error is logged without the value. (Ruled 2026-11-25: this binds THIS module's handle only. The handle keeps no cache of its own, so "the same handle" means a `keys.get` on the handle that issued the rejected `set` returns the stored value or null, never the rejected one, and the module holds no module-level cache of values. The library wrapper `makeCacheableSignalKeyStore` sets its own cache before it calls `store.set`; what it keeps after a rejected write is a property of the composed store, is not judged by this criterion or by C3AB-J1, and is filed as a ledger row, not built here.) (c) 100 parallel `set` calls of one key with distinct values leave exactly one stored row equal to one of them (never a mix) and 100 parallel sets of distinct keys store 100 rows; a storm of `saveCreds` leaves a creds row that decrypts and equals the in-memory creds after the last awaited call. (d) A reader running during a write sees the old or the new value, never a partial one (concurrent get and set, 1000 repeats).
  Check: `npx tsx --test src/wa/authState.test.ts`; the parallel clauses need real conditional writes and run on loopback mongod when present, and on the fake otherwise (the fake run is reported as such).
- **[C3B-C6]** Lifecycle on the database store (D-022, D-013). (a) `destroyAuthState(userId)` with live creds archives the live rows under one new `archiveId` (live rows gone, rows still encrypted, `createAuthState` afterwards yields fresh creds) and returns a non-null archive name; with no live creds it removes only that owner's live key rows and returns `null`. (b) After 6 unlinks of one owner exactly the 5 newest archives remain, in both collections. (c) `hasRestorableAuthState` is true iff a restorable archive exists (not older than the C3B-C8 age limit); `restoreAuthState` returns false and changes nothing while a live link exists, and otherwise restores the newest archive and returns true. (d) `linkedUserIds()` returns exactly the owners that have a live creds row, not owners that have only archives, not half-links with keys but no creds. (e) The creds row is the commit point: archiving moves the creds row first and the key rows after, restore moves key rows first and creds last; a backend that fails after the creds step of an unlink leaves the owner out of `linkedUserIds()`, and repeating `destroyAuthState` completes the rest; a restore that fails midway leaves no live creds, and repeating it completes (no transaction is used). (Ruled 2026-11-25, mechanism: no extra row field is required. A repeat decides whether a live key row belongs to an archive by comparing the row's `updatedAt` with that archive's `archivedAt`, and the creds row is never decided by time (it is the commit point). Both timestamps come from the one store clock (`keyStoreTestSeam.now` in tests). Ties: a key row with `updatedAt` equal to `archivedAt` belongs to the archive, in both the repeat unlink (`<=`: moved into the archive) and the repeat restore (`>` is debris: deleted; a tie is kept). Bounds that must hold under a same-millisecond write, a backwards clock step or skew between two instances: the misclassified row is a key row of the same owner only; no creds row is created, moved or deleted by the comparison; no other owner's row is touched; and `linkedUserIds()` is unchanged by the comparison. A fake-clock test pins the tie (a row at `archivedAt` and one at `archivedAt` + 1 ms) for both repeats. The guarantee assumes one writer per owner at a time, which C3A's lease provides; outside it, the bound above is the whole guarantee. A repeat `destroyAuthState` that moves orphaned key rows into the archive it completes returns that archive's name; it returns `null` only when it moved nothing, which is the no-live-creds case of (a).)
  Check: `npx tsx --test src/wa/authState.test.ts`.
- **[C3B-C7]** Owner isolation [SECURITY CLASS: credential handling, tenancy]. Keys and creds of owner A are not returned by a handle for owner B for the same type and id; deleting, archiving, pruning or restoring A's rows changes none of B's rows (snapshot compare of the raw backend); `linkedUserIds` and `hasRestorableAuthState` report each owner by its own rows; a `userId` that is not 24 lowercase hex is refused before any backend call (including `..`, an uppercase id, an object); every backend query carries the owner id (a recording fake asserts no query without it), with exactly one named exception that C6d makes unavoidable (clarified 2026-11-25, not widened): the query inside `linkedUserIds()`, which may run on the creds collection only, filtered to live rows (`{archiveId: null}`) and projecting only `ownerUserId`. It never reads a key row, never selects `value`, and the recording fake asserts that it is the only ownerless query and that it runs once per `linkedUserIds()` call.
  Check: `npx tsx --test src/wa/authState.test.ts`.
- **[C3B-C8]** Archive age limit (D-025 item 1). (a) Every row of one archive (creds and keys) gets the same `archivedAt` Date at unlink; a live row never holds an `archivedAt`: after any sequence of `set`, delete, `saveCreds` rewrites and a restore, no live row has a Date `archivedAt` (a restore removes `archivedAt` and sets `archiveId` to null on every restored row, so a restored link can never be expired by the index). (b) On a fake clock an archive is restorable at `ARCHIVE_MAX_AGE_DAYS` minus 1 s and not at plus 1 s: past the limit `hasRestorableAuthState` is false and `restoreAuthState` returns false and changes nothing, even though the expiry index has not yet deleted the rows (the server's expiry monitor lags by up to about a minute); an archive whose creds row is missing (partly expired) is never restorable; the 5-newest rule and the age rule both apply. (c) The expiry index is read back from loopback mongod: `expireAfterSeconds` equals `ARCHIVE_MAX_AGE_DAYS` x 86400 on `archivedAt` for both collections. (d) Negative case on a throwaway collection built with the same index definition but `expireAfterSeconds: 1` on loopback mongod: within 90 s a row whose `archivedAt` is in the past is gone and a live row inserted alongside it, with no `archivedAt`, is still there. (e) No module outside the four sibling functions of `authState.ts` reads or restores archived rows, and each takes only an owner id (the `/svc/v1` side is C3A-I4).
  Check: `npx tsx --test src/wa/authState.test.ts`; (c) and (d) need loopback mongod, else NOT-MEASURED for those clauses only; (a), (b), (e) run on the fake.
- **[C3AB-J1] Joint check, C3A with the real key store (run by the checker once both C3A and C3B have a PASS).** On a throwaway loopback database with `KEY_STORE=mongo` and a test key, the C3A unlink route
  test runs with the real key store: unlinking owner A archives A's rows, `linkedUserIds()` no longer lists A, B's rows are unchanged and boot rehydration starts only B. Also (added 2026-11-25): after the unlink route has completed, a `saveCreds` on A's pre-unlink handle (the straggler) is run; the store does not refuse it, so a live creds row and `linkedUserIds()` listing A are expected and not a defect here, but boot rehydration must still start only B, because A's owner state stays `unlinked` (C3A-C7c). Needs loopback mongod, else NOT-MEASURED.
  (checker-kept as the maker wrote it; it is the only check that exercises C3A's unlink and rehydration through C3B's code, so a joint NOT-MEASURED leaves that seam unproven and is reported as such.)

- **[C3B-I2]** The existing cases of `src/wa/authState.test.ts` are updated only by running them over both backends: none is deleted, skipped or weakened, and the count of assertions per existing case on the file backend is unchanged (additions are allowed; no existing assertion is edited) (`git diff HEAD -- src/wa/authState.test.ts` shows the existing assertions intact).

- **[C3B-I5]** No multi-document transaction and no change stream: `grep -rn "withTransaction\|startSession(\|\.watch(" src/wa/authState.ts` is empty.
- **[C3B-I6]** No production database and no network: Mongo tests pass the loopback guard; tests use `./.test-sessions` for the file backend only.

## Out of scope / ignore
Not in this unit: the declarations of names, collections and indexes (C3A); the routes and the lease (C3A); encryption key rotation (the `v: 1` envelope leaves room; no second key is read); operator access to archives (reading or restoring an archive of a service owner is an operator action outside this code and outside `/svc/v1`; D-025 item 1 is the policy); moving existing file sessions into the database (an operator step).

Ruled 2026-11-25 as also out of scope: (1) a write through a handle after `destroyAuthState` is not refused by the store (the file store's ENOENT there is incidental, not a behaviour C3B-C1 compares); the safeguards are C3A's order (socket stopped and logged out before keys are archived, C3A-C7b), the owner's `unlinked` state (C3A-C7c) and the straggler clause of C3AB-J1; (2) the owner-id format check on the file store (C3B-I1 prevails; pre-existing, a hosted run uses `mongo`); (3) what `makeCacheableSignalKeyStore` keeps after a rejected write (see C3B-C5b).

## Stop rule
Stop rule: a finding outside these criteria is filed and not built, except a security-class finding (credential handling, tenancy), which is never capped.
