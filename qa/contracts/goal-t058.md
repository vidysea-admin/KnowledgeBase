| Criterion | Required behavior and evidence |
| --- | --- |
| C1 — Real three-kind synthesis | A user can create an AI FAQ containing useful questions and grounded answers; a report with executive summary, insights, decisions and risks; and a meeting preparation brief useful for the entered meeting purpose. Generation uses an actual configured provider through the established provider seam. Sections containing no supported material say so. Source excerpts alone, hard-coded demos or a renamed generic response do not satisfy these catalogue features. A focused deterministic provider fixture can prove implementation; actual provider/sample outputs are still required for product acceptance. |
| C2 — Grounded factual output | Every factual generated item binds to server-resolved verified claim evidence and actual source turns in the authorized corpus. Stable claim/turn/session/speaker identity, exact source quotation and ordered finite source range are retained; document character offsets remain distinct from recording seconds. Unknown citation identifiers, fabricated quotation, mismatched tenant/session, unavailable sources, unverified/conflicting claims and unsupported factual interpretations cannot render as established facts. Deterministic citation validation and an independent entailment/grounding check refuse or visibly withhold unsupported items. Model verdicts remain model assessments; AI drafts do not become human verification. |
| C3 — Honest uncertainty and safe model boundary | Partial/unavailable coverage, empty sections, provider failure and invalid model output stay visible. Report decisions are attributable decisions actually supported by sources; proposed actions, inferred risks and meeting questions are labelled accordingly and cannot masquerade as historical facts. Source/user text is untrusted data and cannot select a tenant, supply trusted evidence, alter grounding policy, execute instructions or authorize publication. Bounded requests and validated structured responses fail safely without leaking raw source/provider secrets. |
| C4 — Authenticated scope | Actual mounted create/list/read/edit/revalidate/export routes authenticate through the established key middleware and require the appropriate existing scopes. Tenant identity comes only from verified auth. Each selected session/claim/source/output is checked inside that tenant; inaccessible identifiers fail without exposing foreign existence/content. Reads and writes, list filters, exports and production persistence receive independent missing/invalid-key, insufficient-scope and cross-tenant probes. Client-supplied tenant/evidence/generated text cannot replace server authority. |
| C5 — Durable drafts | The production composition supplies a real tenant-scoped persistent repository; outputs survive service/repository recreation and can be listed/reopened. Collection shapes and indexes follow schema-first/generated-type/migration conventions, with tenant-leading indexes and stable natural identities. Writes are bounded and explicit, provider retries cannot produce accidental duplicate publication, and concurrent edits use a revision/CAS boundary rather than silent lost updates. Existing production opt-ins for other stores are not automatically authorization for new T-058 production writes. Verification uses an isolated nonproduction store/database. |
| C6 — Editable and revalidated | The user can edit the resulting draft and save/reopen it. Editing factual text cannot retain stale verified status or silently invent citation mappings. Any needed revalidation is explicit and durable. Source changes/deletion or stale revisions prevent unsafe acceptance/export; fresh checks use current authorized evidence. Adversarial edited fact, citation removal/replacement, concurrent writer and source-drift probes are required. |
| C7 — Export and downstream consumption | A real mounted export produces a usable shareable/editable artifact such as Markdown, preserving factual content, draft/review state, coverage and readable valid citations. HTML/Markdown/user source text is escaped or rendered safely; links derive solely from real authorized source identities and roundtrip through the existing session/turn consumer. Export refuses unvalidated edits or evidence drift, or clearly exports them only as an explicitly unaccepted draft without factual certification. Export and edit downstream consumers are exercised on actual sample-generated output. No external publication/send is inferred. |
| C8 — Product UI integration | A navigable authenticated web surface creates all three kinds from authorized knowledge, displays grounded outputs/coverage/status/citations, saves/loads edits, revalidates when required and exports through the real API. Loading, empty, unavailable, invalid input, provider failure, stale edit and permission/refusal states are truthful and usable. Citation click-through reaches the actual selected source turn. Real shared server/composition, web route/nav/client and persistence wiring must be present; an unmounted router or standalone component is not full-parent delivery. |
| C9 — T-056 dependency | The builder's relationship to T-056 is explicitly documented and exercised through the integrated authorized policy/configuration path where applicable. Required grounding/tenant constraints cannot be weakened by a selected policy. A foundation PASS or module mock does not declare T-056 complete; unresolved upstream integration or acceptance is recorded as a remaining parent gate. |
| C10 — Actual sample and independent live proof | Affected generation/persistence/edit/export stages run green on an actual TOC sample without changing source verification status, raw source bytes or dirty evaluation/media. Immediate downstream UI/source/Markdown consumers use those outputs successfully. D-024 requires independent live-browser evidence for the UI flows (including auth/citation/save/reopen/export); synthetic React/HTTP tests alone do not replace it. Record real-provider provenance and independent semantic assessment of unsupported claims and useful three-kind output. Production writes or browser restrictions are explicit gates, never fabricated evidence. |
| C11 — Established user acceptance | The existing T-058 user-acceptance gate is preserved. Present concrete sample FAQ, report and meeting brief for Umesh's acceptance; record actual response and its scope. An AI reviewer, source-only checker PASS or elapsed time does not satisfy this human gate. Full T-058 completion requires accepted integrated behavior; feasible source implementation can be separately certified while live/provider/human gates remain HOLD. C13/C14 and counsellor T-013 are outside T-058 and cannot be closed by this work. |
| C12 — File handshake and verification | A ready-for-check manifest/packet names the full candidate slug/cycle, changed paths, caller/security/dependency map and final hashes including untracked source. Required focused checks exercise successful stages, refusals, tenant/write/CAS/grounding/drift/export boundaries and immediate downstream consumption, with exact invocation/output/exit/count/duration/fixture provenance. contracts/verify_contracts.py runs with its empty-registry limitation disclosed. Shared integration has schema/generated/migration/type consistency evidence. Only independent checker writes matching-cycle verdict; changed candidate bytes require resubmission, maker closes only after matching scoped PASS. Full-parent PASS requires C1–C11, not selected tests. |
