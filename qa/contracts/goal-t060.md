# T-060 focused acceptance — hosting security runtime

Checker-owned draft, 2026-10-14. Roadmap tier 3; auth, tenancy, writes and credentials require full ceremony and are uncapped. This contract covers the remaining hosting runtime, not an assertion of deployed service, real outbound delivery, or destructive production retention approval.

## Acceptance

- **C1 Verified identity and usable roles.** Mounted authenticated routes obtain tenant and actor/key identity from server-side API-key verification. Tenant membership/role lookup uses that verified identity, never caller-supplied actor, tenant or role headers/body. Unknown, malformed, revoked, unbound and insufficiently privileged callers fail closed. Owner/admin/editor/viewer (or an explicitly documented equivalent) have a tested permission matrix; a lower role cannot grant itself a higher role, elevate key scopes or mutate another tenant. Role assignment/update is a usable authenticated runtime operation with protected administrative boundaries.
- **C2 Durable audit and mutation boundary.** Covered role, key and webhook mutations append tenant-scoped audit records containing verified actor, operation, target, outcome and timestamp, without raw credentials. Successful changes remain discoverable after constructing a fresh store/runtime; callers cannot edit/delete audit history. Audit failure must prevent unaudited mutation success. Intermediate failures must have a defined recoverable state, not a successful response or silently completed side effect. Reads and writes, including supplied foreign IDs and selector-like hostile values, remain scoped to the verified tenant.
- **C3 Webhook registration runtime.** The authenticated registration endpoint is operational, persisted and documented accurately; a competing 501 stub must not intercept it. Registration, listing and revoke/update permissions and tenant isolation are exercised. Signing material is generated securely, returned only at the explicit creation boundary if needed, and never leaked through list/audit/error/status responses. Missing durable dependencies produce a clear fail-closed response.
- **C4 Webhook delivery runtime.** A real callable/mounted production composition path consumes a tenant event and persisted subscription, signs the exact transmitted bytes, invokes a bounded delivery transport, and durably records queued/attempt/success/failure state. Tests exercise an actual local/deterministic transport and immediate consumer, rather than only signature or URL primitives. Non-2xx, timeout, transport failure and absent credentials fail honestly. Stable event/subscription identity prevents duplicate enqueue/success delivery on ordinary replay; retries/restart have explicit documented at-least-once semantics where remote exactly-once cannot be guaranteed.
- **C5 SSRF and secrets.** Registration and delivery reject non-HTTPS destinations, embedded credentials, loopback/private/link-local/reserved destinations (IPv4/IPv6), hostile DNS results and redirects to forbidden destinations. Delivery's address validation is bound to the actual connection, rather than a vulnerable resolve-then-re-resolve fetch. Redirects cannot forward signing credentials. Response/error/log/audit paths do not expose keys, signing secrets or unnecessary payload content. Cross-tenant events cannot target another tenant's webhook.
- **C6 Persistence and downstream proof.** A bounded fixture demonstrates verified auth → authorized mutation → durable audit → registration → signed delivery → delivery status/audit read, then reconstructs the runtime/store and replays/reads without leaking tenants or fabricating success. Concurrent or crash-edge changes have deterministic fail-closed/recovery behavior within the claimed guarantee. Source review includes server/composition, store and immediate consumer. Manifest names exact runtime limitations.
- **C7 Retention scope honesty.** Reuse existing retention contracts and independently verified evidence for retention already implemented. T-060 runtime PASS does not approve production media deletion, alter frozen contracts, or imply live retention execution. Any new retention write/delete in this candidate needs tenant isolation, existing eligibility/evidence-clip preservation guards, an audit failure boundary and explicit authorized scope; otherwise it remains a named whole-task gate.

## Evidence and verdict gate

Maker submits one matching manifest and packet at `ready-for-check`, with slug, fix cycle, changed/caller/consumer map, final SHA-256 hashes, exact bounded commands, exit codes, output artifacts, fixtures, failure probes and remaining gates. Checker independently reviews all new/changed security logic and runs a meaningful focused boundary/consumer probe under the root CPU lease. Applicable `contracts/verify_contracts.py` evidence is retained; full suites, browser work, provider calls, real external messaging and production targets are outside this focused check.

PASS requires all criteria for the explicitly submitted unit scope, with any excluded umbrella requirement named as a remaining gate. HOLD applies to absent packet, changed bytes/cycle, unmounted runtime, missing durable dependency/proof or required checks blocked. A demonstrated criterion violation is FAIL. No primitive-only, fake durable adapter, test-only integration or indirect PASS may establish hosting runtime completion. Verdict certifies only final checked bytes and cycle.
