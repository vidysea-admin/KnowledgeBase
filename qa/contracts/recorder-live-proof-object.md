## Criteria
- **[B4B-C1]** Publish. `BOT_MODE=publish-proof` reads the marker and uploads the file `recording` names to exactly one object `live-proof/<sha256>.<ext>`, where the sha256 in the name is computed independently by the test; the call carries a create-only precondition; the stored bytes equal the local file (`cmp`); exactly one upload call; exit 0. The proof object name is disjoint from the state tar's name, the lease's name and the prefix of B4's recording copy.
- **[B4B-C2]** Snapshot only after a good upload, and failure is loud. In the stub log the state snapshot comes after the successful upload. With a stub upload that exits non-zero (and one that hangs past a short test timeout; checker note: so the upload call must be time-bounded by the entrypoint, with the bound settable by an environment variable for the test), with no marker, with `status` other than `passed`, or with a recording that is missing or zero-byte: the run exits non-zero, writes one log line with a stable text naming the failed proof publish, takes NO snapshot call, leaves no object, and leaves `live-proof.json` byte-equal. A second run with a working stub then uploads once and snapshots.
- **[B4B-C3]** Never overwritten. (a) An object already under the same name with the same bytes: exit 0, no overwrite, the object unchanged. (b) An object under that name with DIFFERENT bytes (pre-seeded): exit non-zero, bytes unchanged, one log line, no snapshot. (c) A later capture's recording with the same file name, copied by B4's recording copy, leaves the proof object byte-equal and lands under a different prefix. (d) A second marker naming another file creates a second object under its own hash and never replaces the first. A test with only the create-only precondition and none of (a) to (d) is vacuous. [ASSUMPTION: "same bytes" is judged by downloading and hashing, or by the object's checksum field.]
- **[B4B-C4]** Restore at start. (checker-clarified: the restore step runs in the same `BOT_MODE`s in which B4's state restore runs and never in `login` mode; `publish-proof` itself does not restore. The manifest names the modes.) In a fresh temp tree, with the stub bucket holding the state tar (which contains `live-proof.json`) and the proof object, the entrypoint puts the media at exactly the path the marker names, byte-equal, after B4's state restore and before the doctor gate and the pipeline (order read from the stub-`node` log). The real `validateRunGate(root, env)` then passes on that tree. The periodic snapshot's tar listing has no entry for the media file.
- **[B4B-C5]** [SECURITY CLASS: data write outside the project root (checker-tagged)] A missing or failed restore leaves the gate closed by itself. With the object missing, the download failing, or the downloaded size differing from the object's: one log line, the entrypoint does not exit because of it (the stub `node` is still started), no file, no zero-byte placeholder and no partial file at the path, and the real `validateRunGate` on that tree throws. A marker whose `recording` is absolute, contains `..`, is a symlink out of the tree, or does not end `.webm`, `.mkv` or `.mp4` is refused at publish AND at restore: nothing is written outside the project root and nothing is uploaded.
- **[B4B-C6]** [SECURITY CLASS: credential and data exposure (checker-tagged)] Not public, no secret. No stub call in any run of the new mode or the restore step sets a public ACL, `allUsers` or `allAuthenticatedUsers`, a public-read flag, a signed URL, or changes IAM (the media is a recording of a real meeting; same rule as B4-I6); the log and the object name carry no token or credential value.
