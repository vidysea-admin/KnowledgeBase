## Judged points (the lead's four plus bypass hunt)
1. Can a dead/revoked/expired cookie session stay signed in (fail-open)? Server side: a dead cookie answers `GET /auth/session` 401 in every case (no cookie: `unauthorized`; revoked/expired: `session_revoked`/`session_expired`; user disabled/missing: currentSession 401; the only non-401 failure is 503 `auth_unavailable` from the authenticator); the router sets `Cache-Control: no-store` on /auth (auth-router.ts:108), so the probe cannot be answered from cache. On the client a dead session ends on the first of: a session code, a 401 on /auth/session, or probe 401. The only fail-open paths are (a) probe answers 5xx/network/hang (point 2) and (b) a probe that answers 200 with a non-API body (reverse-proxy fallback; own test B1 stays signed in). Both are bounded by "the next real request re-checks", and the person is not shown data (the feature still gets its ApiError and shows unavailable). Acceptable.
2. Probe on 5xx/network: person stays signed in, feature shows unavailable, the next 401 re-probes (own test B7: a later request after the outage ends the session). Acceptable. A probe that never answers is different: see PROPOSED-ISSUE 1 (no timeout; the feature request hangs and the shared probe stays wedged). That is a liveness defect, not an auth hole.
3. Wrong-password login 401 while a session is held no longer signs it out: safe, arguably a fix (the login form is not shown while signed in; a failed guess should not end an unrelated live session). Own test B4: alive -> no event; session actually dead -> one event. With no session held, the extra `GET /auth/session` fires and may dispatch an invalidation event, but AuthContext.handleAuthInvalidated ignores it (`keyRef.current === failed` is false when signed out, AuthContext.tsx:127-141), so the login page still shows the thrown ApiError text (user-accounts.ts:137 maps `invalid_credentials`), not "sign in required". One wasted request per failed login; not a defect.
4. Concurrent 401s share one probe: own tests B5/B7/B8. A probe started before a revoke can be shared by a 401 sent after it (stale 200), leaving the person signed in for one more request; the next 401 starts a fresh probe (sessionProbe is cleared on settle) and ends the session (B7, informational). A 401 landing after the probe settled starts a second probe and can dispatch a second event for the same dead session (B5, benign: the handler is idempotent). A probe answering after sign-in/out replaced the login is dropped by the existing `sentSession !== authSession` guard (builder test plus my stale-guard mutant red). No race leaves stale auth state beyond one request. The csrf-403 replay path is untouched (B8).
5. Bypass hunt, no further finding: `/auth/session?x=1` is treated as the identity check (immediate); `/auth/sessions` (the list) is probed, not immediate (B3); a probe 401 with a non-JSON body falls back to the original message (B2); a 403 never reaches the probe; an API-key 401 is unchanged (no probe, same event, storage cleared).
