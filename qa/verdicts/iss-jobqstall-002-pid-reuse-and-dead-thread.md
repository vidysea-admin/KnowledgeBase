## EXPLANATION

Guarantee I certify: on one host, a queue lock whose holder died but whose pid answers is no longer a 1 h write outage when (a) the pid was reused by a process the OS reports as started more than 1 s after the lock was written (taken over once the lock is 30 s old), or (b) the holder was a worker thread (id > 0) that has held the lock 60 s (taken over at 60 s). A live main-thread or other-process holder keeps the 1 h protection of ISS-JOBQLOST-003. A displaced holder that is checked before its last check gets `conflict` and writes nothing.
Before-wiring conditions of ISS-JOBQUEUE-002 that remain (row left `open-before-wiring`): ISS-JOBQLOST-001 (no pruning, growth, medium), ISS-JOBQSTALL-001 (a displaced holder can still clobber in the few instructions after its last check, low), and now also ISS-JOBQPID-001 (the same window reached by a live worker thread stalled over 60 s, low). The pid-reuse / dead-thread condition (ISS-JOBQSTALL-002) is closed within the limits below. Separate from wiring: ISS-JOBQPID-003 (medium, a flaky shipped test, see 4).

1. Clock sources. Windows start time is `StartTime.ToUniversalTime().ToString('o')` parsed with `Date.parse`: UTC end to end, culture invariant, so time zone and DST cannot shift it (this box is UTC, so the zone offset itself is not exercised; by construction it cannot matter). Real child: start time minus spawn time = 5-6 ms, 3/3. Injected: a LIVE genuine holder is displaced iff `at < start - 1000` and the lock is >= 30 s old: at = start-1001 displaced, -1000 and -999 conflict, a start inside the 1 s slack conflict. So a live holder can be judged "started after the lock" only if the wall clock stepped BACK by more than ~1 s (plus the holder's pre-lock run time) between process start and lock write, AND the lock is already >= 30 s old (a stalled holder). Own-pid and Linux estimates (`Date.now()-uptime`, `btime`) shift with a forward clock step or a suspend. Consequence is bounded: the displaced holder's `stillHeld()` + content re-check still runs (C5 below), so it is the ISS-JOBQSTALL-001 window, not the old age-only loss. Judged low, same class as the age rules already in the lock; not filed.
2. PowerShell. Pid reaches the command only as a `Number.isSafeInteger` from the lock JSON (strings, arrays, 1e30, 5.5 never reach `startTime`: 0 lookups; they take the old unverifiable rule), so no injection. Missing powershell (bad SystemRoot) null in 1 ms; powershell exiting non-zero with no stdout null (533 ms); hung process hits `spawnSync` timeout (measured ETIMEDOUT, empty stdout) then NaN then unknown, so the old 1 h rule. Real lookup 435 ms. One lookup per call, only for a live foreign lock >= 30 s old, never on the hot path; the lookup is synchronous and not bounded by `lockWaitMs`, so such a call can take up to 5 s (typically 0.4 s) before returning conflict. Acceptable, noted.
3. Thread lease. Real worker, parent at wallNow +61 s: stalled before the post-lock check -> parent ok, worker `conflict` ("queue lock was lost before the rename"), stored [fromParent]; stalled exactly at the rename -> both ok, stored [fromWorker], the parent's acknowledged write is LOST. So for threads the lost update is reopened in the window after the last check only (ISS-JOBQSTALL-001 / ISS-JOBQPID-001), instead of 1 h protection. It is honestly stated as the residual in the manifest and header; `stillHeld()` and the content re-read are still in place (saveQueue line 82-83). A healthy critical section is milliseconds, so a live worker holding past 60 s means it is already stalled. Ruling: not a hidden regression, correctly filed low; wiring should keep it listed.
