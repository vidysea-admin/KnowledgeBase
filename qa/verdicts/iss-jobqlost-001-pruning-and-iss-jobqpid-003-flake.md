1. Pruning safety (re-derived from the diff and by reading the tests).
- Result not yet read: the queue stores no job result. `complete` returns the job to the caller in the same call; there is no read/status API. What pruning loses is the id: a late `complete`/`fail`/`heartbeat` of a pruned job answers `not-found` instead of `terminal`, and a re-enqueue of the id returns `enqueued` (new job) instead of `exists`. Pinned by tests, documented, filed as ISS-JOBQPRUNE-001. The retention must exceed the longest producer retry and late-ack horizon.
- `dead` jobs: pruned like done after the retention. There is no retry/requeue API in the interface, so no operator path is lost today; if one is added, the dead-job retention must be reconsidered (note for the wiring unit).
- Lease -> complete -> pruned while a duplicate enqueue races: every operation is under the one queue lock and one atomic save, so they serialise. Same-id enqueue inside the retention: `exists`. Same-id enqueue exactly when expired: that enqueue still answers `exists` (prune runs after the change; test "pruning forgets the id") and the job is dropped in that save; the next enqueue gives a new job. Benign, the original job did finish.
- Jobs terminal BEFORE this change (no stamp): stamped `now` on the first pruning-enabled successful operation (all tenants' unstamped terminal jobs get the stamp; only the caller's tenant can be removed) and age from then. So never pruned immediately and never pruned without a stamp. Safe, tested (older-build case). Side effect: one stamping write even on an operation that would otherwise save nothing.
- Clock backwards: `now - terminalAt >= keep` is false when negative, so nothing is pruned; tested. A far forward step prunes what is then older than the retention, as intended.
- Tenant isolation: the filter requires `j.tenantId === tenantId`, where tenantId is the operation's `input.tenantId` / `opts.tenantId` / `ref.tenantId`. An op naming no tenant prunes nothing. A ref naming another tenant's job fails `owned()` (not-found), so `r.ok` is false and nothing is pruned or written. A failed change prunes and writes nothing (tested). Tenant A's op never removes B's job (tested; my mutation 2 killed).
- Atomicity: no new fs calls; create/rename/unlink sequence equal on vs off (test); a crash at 60 points leaves the old or the new complete decodable file (test). nextSeq never rewinds. New decode rule: `terminalAt` allowed only on done/dead as a non-negative safe int; nothing wrote the field before, so no existing file becomes corrupt.
