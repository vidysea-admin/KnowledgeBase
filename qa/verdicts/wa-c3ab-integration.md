## Rulings requested
1. **Straggler clause and ISS-C3BKEYSTORE-001 (medium).** Measured and real at the key-store level: after unlink, a fresh pairing of the same owner, a stale held handle's `saveCreds` resolves and overwrites the new creds (observation O1: `H1-old` replaced `H2-new`). It does not break J1 as written, because J1's straggler runs after the unlink with no relink in between, and that holds from the key store alone. End to end on the `/svc/v1` surface the precondition is unreachable: an unlinked owner is sticky (J1-5: session and QR routes return 409 `owner_unlinked`, `POST /owners` returns the existing owner as `unlinked`, `created:false`, and no handle is opened), so a fresh pairing on the same owner cannot occur through C3A. It stays reachable only by an operator restore or a non-hosted path. Ruling: the issue stays open at medium as a key-store property, is not a J1 failure, and does not block. The same holds for a stale held handle after `restoreAuthState` (J1-6 restores after the stragglers and asserts only restorability).
2. **ISS-011 and ISS-012 (old behaviour rows).** Observed both: O3 (a pairing handle's first upsert overwrote the row another instance created) and O2 (a handle opened before `restoreAuthState` overwrote the restored creds with `stale`). Neither breaks J1 as written: J1's A has a live creds row when its handle opens and nobody opens a handle before a restore. Both stay open at low, unchanged.
3. **Owner isolation (C3B-C7, security class).** Holds. With two and three owners present, unlinking one never changed another owner's rows (J1-1, J1-2, J1-6, J1-9, byte comparison of users, creds and keys). Falsified: dropping the owner filter from the creds archive (M5b), from the key archive (M4) are both killed (M5 survived the first harness, because A was the oldest owner; I added J1-9, target created last, and M5b then dies).
4. **`LINK_GONE` only logged (`index.ts:142`).** Acceptable under the straggler clause. Measured in the real process (J1-8): the listener's rejection surfaced as exactly one unhandled rejection with code `LINK_GONE`, the process stayed up (`exited()` still running, `/svc/v1/health` 200), nothing was written (live creds for A stay 0, archive count stays 1), and neither child's output contains the encryption key, the service token, the seeded key bytes or the canary. The clause wants a rejection, not a crash. Low observation: the safety of that path rests on the handler at `index.ts:142`; remove it and Node 24 would turn the rejection into an exit.
5. **`ERROR builder-suite` lint (kept on purpose per D-243 item 5, true suite_runs=1).** A process matter, not a product failure. The suites it concerns are green (E4 to E6). No effect on J1.
6. **`src/db/mongo.ts` logging the full MONGO_URI.** Out of scope. In this tree the connect log is `mongo.ts:40`, `{host: safeUriHost(config.mongoUri), db}`, and the real-process log scan found no URI credential; the evidence shows it does not touch J1.
