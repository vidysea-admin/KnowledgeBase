## Judge points asked for
1. Fail-open (a dead/revoked/expired cookie staying signed in): not found. Revoked/expired are immediate. Every other dead state (cookie gone, session row deleted, proxy 401 with an HTML body) reaches the probe, which answers 401 on a dead cookie and cannot be cached. The only states that keep a dead session signed in are probe 5xx or no network (point 2) and a probe that never answers (P1). In all of them the next real request re-checks, and the server refuses every call regardless, so only the UI shell stays, not access.
2. Probe on 5xx / network error: stays signed in, caller still receives its ApiError. Acceptable. The server is authoritative on every request; a transient 503 from the session store (exactly what `auth_unavailable` is) ending a valid session would be the worse error. The accepted cost is that a dead session shows "unavailable" on that screen until a request gets a real answer.
3. Wrong-password login 401 while a session is held no longer signs the held session out: safe, arguably more correct (a failed login proves nothing about the held session; the server keeps it alive). Confirmed by A4: no event, calls = `/auth/login`, `/auth/session`. Side effect: every wrong-password login, including the common signed-out one, now waits on one extra GET /auth/session before its error shows; that probe's 401 event is ignored by AuthContext (`keyRef` null). Latency and one more console 401 line, not a defect (see P2).
4. Concurrent 401s sharing one probe: no stale-state race found. The slot is keyed by the login (`sessionProbe.session === session`), cleared by identity after settle, `announced` dedups the event per probe, and `invalidateAuth` drops results for a replaced login (A5). Harmless, documented: a `session_revoked` and an `unauthorized` 401 in flight together yield two events for one session end (A6: 2 events); AuthContext's handler is idempotent. One real weakness: no timeout on the probe (P1).
