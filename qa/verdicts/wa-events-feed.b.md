## Judged points
1. Reader scope and tenancy. `requireScope("whatsapp-admin")` is an exact-match array check (auth.ts:107); roles.ts grants it to ADMIN only; unauthenticated is stopped by requireAuth (401 in the real-server test); tenant is `req.auth.tenantId` only (my tenant-override mutant is caught); the accessor `list` calls a tenant-scoped `findOne({_id: afterId})`, so another tenant's id gives the same `unknown cursor` 400 as a missing id (packages/db test at whatsapp-links.test.ts:123). The route is mounted behind the shared auth perimeter; with no feed wired it stays behind the scope and answers 503. No bypass found for member, viewer, unauthenticated or other-tenant callers.
2. R-39 payload. Free strings can only enter through `reason` and `errorCode`; both are pinned by schema pattern `^[a-z][a-z0-9_]{0,63}$`; the HTTP layer already restricts `reason` to that code shape (links/router.ts `code()`), `errorCode` in runEvent is clamped to ERROR_CODES else `unknown`, and error strings never reach event data (event writes catch and log `code` + `eventType` only). `candidateId` is `wa-review:<sha256 of a tuple that includes tenant and source>`, not guessable from content. `actorId` is `user:<id>`, the key id, or `api-key-sha256:<hash of the bearer>`. The archiver owner id never reaches data (the lifecycle test plants it as a canary). I also ran a scratch probe in the copy: with the production default sink (no appendEvent override) an ingest through the real `createWhatsAppReviewWiring` wrote one `candidate.created` row under `tenant-a` that validates by hand against `schema/whatsapp_events.schema.json` (enum, key set, patterns), so the best-effort sink is not silently dropping on a schema mismatch.
3. candidate.created granularity (builder open point 1; reported, not decided). Head emits one `candidate.created` per ingest with `data.count`. R-38 lists `candidate.created` without a cardinality; C1 says "exactly once per transition". If the transition is "a candidate is created" the feed under-delivers (a consumer learns N appeared but no ids and must poll the review API); if it is "an ingest proposed candidates" it is exact. The repository `insert` returns a count only, so per-candidate events need that port to return ids (no schema change either way: `candidateId` is already a data key). Product intent for the lead. Related declared point 2 stands: a system rejection of pending candidates on unlink/revoke (store.ts:226) writes no `candidate.rejected`, covered by the link event.
4. Failed event write never breaks the transition. Review router: `emitBestEffort` try/catch, awaited after commit, response unchanged (events.test failing-sink test; removing the await is behaviour-equivalent). Ingest: same helper. sync-links: `persist()` records the run first, then `.catch`es the append; the `deps.alert` result is also `.catch`ed. Residual: `deps.appendEvent(...).catch(...)` would throw synchronously if a future port were a non-async function (second proposed issue). The wired port is `async`.
5. No webhook/registry/outbound call. None added (own diff grep above). The events surface registers exactly one GET plus one header `use`.
