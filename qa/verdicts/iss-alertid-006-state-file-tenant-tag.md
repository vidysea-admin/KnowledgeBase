## EXPLANATION

Isolation (tenancy):
- Every reader of these two files in the repo is converted. Whole-repo grep (packages, apps/api, apps/web, scripts, *.ps1, *.py, *.mjs) for schedule-state, `scheduled/`, raw/webinars and the read/write function names: the only parsers are schedule-state.ts (tag-checked), schedule-tick.ts, alert-who-command.ts (its own parser, `assertTenantTag` on state and on every job file) and send-now-command.ts `readLiveJobs` (its own parser, `assertTenantTag` after the shape check). scripts/webinar/*.mjs import only validators, which read operations.json, not these files. apps/api and apps/web do not read them. tsc passes, so no caller still uses an old signature.
- Forged or edited tags: the compare is exact (`tag !== tenantId`, no case folding). A tag of the wrong type, empty, an array/null/number body, wrong key case (`tenantid`), an upper-cased tenant, and a session key named `tenantId` are all refused (test cells). The tenant must match the host regex before use; `""`, undefined, null, non-strings, `../b`, `a/b`, `a\b` and 101 characters are refused and nothing is created. The tenant never reaches a path (the state dir is fixed; only the hashed jobKey names files). Messages never name the other tenant or print contents.
- Writers read (and so tag-check) before writing, so a foreign or untagged file is never overwritten by the TypeScript writers. Residual, low: (1) the check and `writeFileSync` are not atomic (read then write, no re-check at rename, no temp+rename); a file swapped in between would be overwritten. That needs a concurrent local writer inside a millisecond window, and a local writer can forge the tag anyway. (2) An UNPARSEABLE schedule-state.json or job file is treated as empty/null as before and the next write replaces it, including another tenant's corrupt file. It holds no readable data. Neither is a cross-tenant read or resolve.
- ISS-ALERTTENANT-001 (scripts/webinar/start-record-detached.ps1 `-Job`): I read it. It reads `url/until/title/sessionId` from `raw\webinars\scheduled\<jobKey>.json` (key validated `^[a-z0-9-]{1,64}$`), ignores the tag, and launches a recording of that URL. It is invoked by a Windows task the tick registers only AFTER `writeScheduledJob` succeeded for that key, and `writeScheduledJob` now refuses a foreign or untagged file at that key (the item is skipped before any task exists). So this unit's code paths cannot steer it across tenants; only a locally planted file could, and that can carry a forged tag. It returns nothing to a caller. Medium is right; it is a hardening item, not a hole in this unit's criterion. Tasks registered before the merge (untagged job files) still launch normally.
- Order note: the tick fetches calendar events and candidates before `requireStateTenant` runs, so an unset `LKB_TENANT_ID` costs two API reads before the throw. It still throws before any state read or write; the manifest's "before reading state" is accurate.

Two tenants, one directory (ISS-ALERTTENANT-002):
- The first tenant to write claims `raw/webinars/schedule-state.json`. The second tenant's tick then throws `StateTenantRefusal` (other-tenant) on every tick, for ever, until the files are moved aside or its `stateDir` differs; it never overwrites and never interleaves (tested: tick throws, schedules nothing, tree byte-identical). A foreign `scheduled/<key>.json` makes only that item skip. alert-who and send-now for the losing tenant show warnings or "cannot tell". So "tagged but shared path" closes the leak half of ISS-ALERTID-006 (no read, resolve, overwrite or delete across tenants through these files) but not the "one shared path" half: two tenants still cannot coexist on one machine.
- The fix_direction reads: "per-tenant stateDir (raw/webinars/<tenant>/) or a tenantId field in both records validated on read, plus a migration for existing untagged files." The second alternative was chosen; the migration is absent. docs/webinar-release.md describes one operator tenant per machine, so I accept this as an honest closure of the ISOLATION criterion, not of multi-tenant coexistence or the migration. I left ISS-ALERTID-006 OPEN for that reason (migration clause unmet; tracked as ISS-ALERTTENANT-003 low and ISS-ALERTTENANT-002 medium). The Approver may close it on the isolation criterion alone.

A mis-set variable gets files tagged with the wrong tenant name. ISS-ALERTTENANT-002 stays medium because the larger half lives in those two already-high rows.
