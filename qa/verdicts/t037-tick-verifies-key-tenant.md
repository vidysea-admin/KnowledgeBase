## EXPLANATION
1. The header IS the key's tenant (API side, read-only). `GET /webinar-operations` (apps/api/src/routes/brain.ts:174-179) sets `X-LKB-Tenant` = `req.auth!.tenantId` only on the 200 path (including an empty result). `req.auth` is assigned in exactly one place, `requireAuth` (auth.ts:58), from `ApiKeyStore.verify(bearer)`, which reads the tenant from the stored key record (store.ts:44-47) and refuses an unusable tenant with 401. Not from query, body, other headers or env. 401 (no/bad key), 403 (missing `sessions`) and 503 (state unavailable) carry no header, so a missing header means unknown. server.ts mounts requireAuth before the router and nothing strips or rewrites the header. A caller can only learn the tenant of the key it already holds. Not caller-controllable.

This is exactly the documented fail-open meaning. Plainly: under fail-open an operator who misconfigures the tenant (or whose key cannot be verified) gets enforcement that silently does nothing apart from one log line; opt-outs and deny rules are not honoured and the meetings are recorded. Fail-open therefore does not protect against the very condition this unit detects.
