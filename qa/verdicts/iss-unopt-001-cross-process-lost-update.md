## EXPLANATION

Guarantee I certify: un-opt (`recordTenantUnOptOut`), opt-out and approval each do their whole load, change and write inside the one per-tenant lock, so an acknowledged change of those three is not overwritten by another of them in any mix of processes. A writer that cannot get the lock, loses it before the rename, hits a corrupt file or a failed rename throws a typed error and writes nothing; the opt-out stays in force. NOT certified: PUT (see below).

- Row read: ISS-UNOPT-001 (qa/issues.unopt.jsonl) records one scenario, "a second writer process could lose an approval/opt-out made between the load and the save". The test asserts that text by regex, then replays it: 4/4 (approval and opt-out each refused with `locked` and writing nothing, then applied on retry with the un-opt kept). The control shows the old shape loses the approval. Caveat: the replay's second writer is an in-process nested call inside `afterRead` (it gets a real `locked` from the live lock), not a separate process; real processes are covered by the 3-process test.
- Counts I re-ran: unopt-lock 5/5; join-rules-store 21/21; store-lock 22/22; join-rules-host 14/14; join-rules-edit-api 4/4; apps/api un-opt 9/9. All use localhost test servers or temp dirs only (the host test spawns only `node` helper processes); no browser, OBS or network. 3-process x 6-round test alone: 20/20 runs green, no EPERM/EBUSY/EACCES or any other error code seen. The lock treats EPERM/EBUSY/EACCES on create as contention (stat afterwards) and a failed lock read as "not ours", failing toward `locked`.
- Which copy the scripts test ran: `scripts/webinar/join-rules-host.ts` imports the store by RELATIVE path (`../../packages/meeting-bot/src/.../join-rules-store.js`), and `join-rules-host.test.ts` does the same, so it ran the lane's copy, not the main tree's. Proven: a temporary `throw` at the top of the lane's `recordTenantUnOptOut` turned 3 of 14 host tests red (M0). Touching `scripts/webinar` was necessary: the adapter is the only caller of the un-opt path.
- Writers of the state file (all of them): `saveJoinRules` (PUT, via deps.save): lock only around the write, snapshot supplied by caller, NOT a locked read-modify-write; `recordTenantApproval`, `recordTenantOptOut` (`mutateState`): inside the lock; `recordTenantUnOptOut`: inside the lock (new); the scheduler tick / `join-rules-enforce` only READ (`loadJoinRules`, no lock, any read error skips every meeting under fail-closed); no script, PowerShell or other writer exists.
- PUT versus opt-out (the question that matters): TODAY a PUT can erase an opt-out. Rule set and state live in one file; the router PUT does `existing = load()` then `save({ruleSet, state: existing.state})`. I ran it with a second real process opting out between the PUT's load and save: file showed `['cal1']`, after the PUT it showed `[]` and `evaluateJoinRules` returned `join`. It is not reachable inside the one API host (the router chains PUT/approve/opt-out/un-opt per tenant in process, and the host pid lock allows one host), so it needs a second writer process: the same precondition that made ISS-UNOPT-001 medium. Severity medium; this unit leaves it UNCHANGED for PUT (and narrows the surface by locking un-opt). Filed as ISS-UNOPTLOCK-002; the maker had only a prose note, no ledger row. Out of the stated criterion (un-opt), so not FAIL.
- Fail direction: busy -> `locked`, bytes unchanged, decision still not `join` (tested); lock stolen mid-operation -> `locked` before the rename, bytes unchanged (tested, and M2/M3 go red); failed rename -> `write-failed`, opt-out kept; corrupt file -> `corrupt`, bytes unchanged. The router maps every store error (locked 503, others 500) so a failed opt-out or un-opt is never reported as done. Un-opt cannot lift a veto except by a completed rename.

## Operational consequence of merging

An un-opt now waits (up to 5 s) for the tenant lock and answers the existing 503 `join_rules_busy` instead of silently succeeding on a stale snapshot; a no-op un-opt also needs the lock. No data migration, file format or dependency change. Merging does NOT stop a PUT of the rule set from erasing an opt-out made by a second writer process after the PUT's load (ISS-UNOPTLOCK-002); with the single API host plus pid lock that cannot happen today, so do not start a second writer (script or second host) until PUT is made a locked read-modify-write.
